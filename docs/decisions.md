## R12 CRM (2026-10-03)
- Migration number: CRM is `V23__crm.sql` (V22 was taken by MRP); PLAN R12-1.1/1.2 say V22.
- Permissions: besides the four in R12-3.3 (`LEAD_MANAGE`, `OPPORTUNITY_MANAGE`, `QUOTATION_CREATE`, `CUSTOMER_ACTIVITY`) there is `CRM_VIEW` (read everything), `PRICE_LIST_MANAGE` and `CUSTOMER_TAG_MANAGE`. Each endpoint declares one authority. `CRM_AGENT` gets the four plus `CRM_VIEW`, `SALES_VIEW`, `PRODUCT_VIEW` (needed for the product picker), `REPORT_VIEW`, `DASHBOARD_VIEW`; `SALES` gets `CRM_VIEW` + price and tag management; `ADMIN` gets all seven. No demo CRM user is created (no demo-user mechanism, as for CONTROLLER and PLANNER).
- Lead machine is strict: NEW -> CONTACTED -> QUALIFIED -> CONVERTED; UNQUALIFIED from any open state with a mandatory reason (`disqualify_reason` column added to DESIGN 18.1). Converted/unqualified leads are terminal and not editable. Endpoints are per transition (`/contact`, `/qualify`, `/disqualify`, `/convert-to-opportunity`), never a free-form status update.
- Lead conversion creates a customer (code `CUS/YY/NNNNN` from DocumentNumberService, name and contact details from the lead) unless an existing customer id is given, opens a PROSPECT opportunity inheriting contact, value, close date and owner, links the contact to the customer, and moves activity logged against the lead into the customer's log.
- Opportunity machine is forward-only: PROSPECT -> QUALIFIED -> PROPOSAL -> NEGOTIATION -> CLOSED_WON, CLOSED_LOST from any open stage with a mandatory reason. The stage sets the probability (10/25/50/75/100/0). Converting a quotation links it (`converted_quotation_id`) and closes the opportunity as WON when it is in PROPOSAL or NEGOTIATION; earlier stages are linked but left open. The board moves cards with buttons, not drag and drop.
- Quotation: DRAFT -> SENT -> ACCEPTED -> CONVERTED, SENT -> REJECTED (reason), DRAFT/SENT -> EXPIRED (daily sweep 01:15 and a check on accept). Columns added to DESIGN 18.1: `payment_terms`, `notes`, `sent_at`, `responded_at`, `reject_reason`. Default validity is setting `crm.quotation.default_validity_days` (30). The net unit price is `unit_price x (100 - discount) / 100` rounded half-up to 4 places and the line total is quantity x that net price, so the sales order created on conversion (which stores only the net unit price) totals exactly the quotation.
- Conversion needs `QUOTATION_CREATE` and creates a DRAFT sales order through `SalesOrderService` (approval still needs `SALES_APPROVE`); CRM never touches sales entities or repositories directly (ArchUnit).
- Pricing (R12-4.1): one table `customer_prices` instead of `price_lists` + `customer_prices`; a null `customer_id` is the standard price. Precedence among rows valid on the date and reachable by quantity: customer-specific beats standard, then the highest `min_qty`, then the latest `valid_from`. A quotation line with no explicit price and no price list row is rejected.
- Segmentation (R12-4.2): `customer_tags` (group INDUSTRY/REGION/TIER/STRATEGIC/OTHER + name) and `customer_tag_assignments`; `GET /api/crm/customers?tagId=` lists customers with their tags. The partner module's customer API is untouched.
- Activities store the customer on every row, derived from the contact, opportunity or lead when not given; at least one of customer, contact, lead or opportunity is required (DB check). Contacts are deactivated, never deleted.
- Pipeline report (R12-4.3) `CRM_PIPELINE` is in the report catalogue (authority `CRM_VIEW`). CSV export is done in the browser; XLSX and PDF export are NOT implemented because the platform has no report export infrastructure yet - do that once for every report rather than per module.
- FIXED (2026-10-03): `@Query` searches written as `(:q IS NULL OR LOWER(x) LIKE LOWER(CONCAT('%', :q, '%')))` failed on PostgreSQL with `function lower(bytea) does not exist` when `q` was null, so list endpoints without a search term returned 500. Affected `CustomerRepository`, `SupplierRepository`, `MaterialRepository`, `ProductRepository`, `UserRepository` and `WarehouseRepository`. Pattern now in force: the query uses `(:q = '' OR ...)` and each repository exposes a default `search(...)` that normalises null/blank to "" via `common.search.SearchText.normalise`, so callers and API behaviour are unchanged. Covered by `SearchIT` (absent, blank, whitespace, matching and non-matching q on every list endpoint). New text-search queries must follow the same pattern (CRM's Specification-based and `:q = ''` searches already did).

## R13 HRM (2026-10-03)
- Migrations: HRM core is `V24__hrm_core.sql` and payroll is `V25__payroll.sql` (V23 was taken by CRM); PLAN R13 says V23/V24.
- Permissions: besides `EMPLOYEE_MANAGE`, `PAYROLL_RUN`, `ATTENDANCE_MANAGE` and `LEAVE_APPROVE` (R13-5.2) there are `HR_VIEW` (read employees without pay data, skills, attendance, leave, training) and `LEAVE_APPLY` (self-service; granted to every role so any employee can apply for their own leave). `HR_VIEW` is also granted to PRODUCTION_MANAGER and SUPERVISOR so planning can see who is authorised on a machine. The `HR_MANAGER` role is seeded; as for CONTROLLER and PLANNER no demo user is created because the repository has no demo-user mechanism.
- Pay and bank data (`basicPay`, allowances, bank, PF/ESI numbers) is returned only to callers holding `EMPLOYEE_MANAGE` or `PAYROLL_RUN`; everyone else gets `compensationVisible=false` and nulls. Every payroll endpoint, including reads of runs and slips, needs `PAYROLL_RUN`. Changing basic pay or fixed allowances requires a reason and writes `EMPLOYEE_PAY_CHANGE` to the audit log with the old and new figures.
- Columns added to DESIGN section 19.1: `employees.date_of_leaving`, `fixed_travel_allowance`, `fixed_other_allowances`, `default_shift` (DESIGN's slip has travel and other allowances but the employee had nowhere to hold them); `attendance.source` (MANUAL or AUTO); `leave_types.paid` and `max_carry_forward_days`; `leave_applications.half_day`, `decided_by`, `decided_at`, `decision_reason` (replacing DESIGN's `approved_by`/`approved_at`, because rejection and cancellation are decisions too); `payroll_slips.da` and `cost_centre_id`; `payroll_runs.approved_by`, `paid_at`, `paid_by`, `payment_journal_header_id`. New tables: `shifts` (R13-2.1), `leave_balances` (ARCHITECTURE section 19), `training_records` (DESIGN names it but defines no columns; shaped from HRM-006).
- Payroll run states are DRAFT -> COMPLETED (approved, journal posted) -> PAID. DESIGN's PROCESSING value stays legal in the database but is never entered because slip calculation is synchronous.
- Attendance rules: a working day is any day that is not a weekly off (`hrm.weekly_off_days`, default SUNDAY) and not recorded HOLIDAY for that employee. Unrecorded days are governed by `hrm.payroll.unrecorded_day_policy` (V26): ABSENT (default) makes a working day with no attendance row and no approved leave loss of pay; PRESENT keeps the original behaviour where only explicit ABSENT (1 day), HALF_DAY (0.5) and unpaid-leave days reduce pay. Weekly offs, HOLIDAY days and approved paid leave (including paid half-day leave) are never penalised, and days from today onward are never penalised, so a mid-month run does not dock the rest of the month. The policy that applied is written into the PAYROLL_CALCULATE audit entry. Approved leave overrides an absence on the same day. There is no holiday calendar table; HR marks HOLIDAY through the bulk attendance endpoint.
- Pay proration: factor = paid days / working days in the month; joiners are paid from the joining date and leavers to the leaving date (the days outside employment count as loss of pay on the slip). Basic, HRA, DA and the fixed allowances all prorate. Amounts round HALF_UP to 2 decimals, day counts to 1.
- Statutory figures are `system_settings` rows (`hrm.payroll.*`), never code. Seeded defaults: HRA 40%, DA 0%, PF 12% + 12% on basic capped at 15,000, ESI 0.75% + 3.25% when gross <= 21,000, professional tax slabs `7500:0,10000:175,:200`, and simplified TDS (projected full-month gross x 12, less a 75,000 standard deduction, new-regime slabs `300000:0,700000:5,1000000:10,1200000:15,1500000:20,:30`, 1,200,000 rebate limit, 4% cess, spread over 12 months). HR and finance must review these every financial year; the PT slab is a Maharashtra-style placeholder. A calculation that would produce a negative net pay aborts the run and names the employee.
- Payroll journal: approval posts one balanced journal through the new `JournalService.postSourceJournal` (same transaction as the run, unlike `postAutoJournal` which is REQUIRES_NEW for AFTER_COMMIT listeners): Dr 5201 Salary Expense, 5205 Employer PF, 5206 Employer ESI (per cost centre of the employee), Cr 2501 Salary Payable (net), 2502 PF Payable, 2503 ESI Payable, 2504 Professional Tax Payable, 2505 TDS Payable. Posting date is the last day of the payroll month, so that fiscal period must be OPEN at initiate, calculate and approve (rule 14). Marking the run paid posts Dr 2501 / Cr 1201 Main Bank on the chosen payment date. HRM reaches finance only through JournalService (ArchUnit).
- Approval freezes the month: attendance and leave changes for a month with a COMPLETED or PAID run are refused (`PAYROLL_LOCKED`), including auto-capture.
- Leave: balances are per employee, leave type and calendar year of the application's first day; the row is created on first use with the type's entitlement and a carry-forward capped at `max_carry_forward_days`. No pro-rata entitlement for mid-year joiners. Unpaid types (LOP) and types without a yearly maximum carry no balance. Pending requests do not reserve balance; it is checked again on approval. Nobody approves their own leave (`SEGREGATION_OF_DUTIES`). Approving writes LEAVE attendance rows for working days that have no record; cancelling an approved leave removes them and restores the balance.
- Attendance auto-capture (HRM-002): the production service publishes `OperationStartedEvent` and `OperationCompletedEvent`; an AFTER_COMMIT listener in HRM sets check-in (earliest start) and check-out (latest completion) for the employee linked to the operator, in its own transaction and never failing the operation. The operator is the operation's assigned operator, else the user who acted. Holiday, leave and half-day records are left for HR.
- Skill matrix (HRM-005): `GET /api/hrm/skills/authorised?machineId=&operationId=` lists active employees with a non-expired authorisation; R18 scheduling will call it. `GET /api/hrm/employees/unlinked-users` lists OPERATOR and SUPERVISOR users with no employee record (MDM-041).
- Pay slips: the project has no PDF library, so the slip is a print-friendly page and "download" is the browser's print / save as PDF.
- Run numbers `PAY/YY/NNNNN`, leave `LV/YY/NNNNN`, employees `EMP/YY/NNNNN` follow the implemented document-number format.
- FIXED: `AuditService.asJson` let text that merely begins with a number or literal (for example `2 slips; gross ...`) through as "valid JSON" because Jackson ignores trailing tokens; PostgreSQL then rejected the JSONB insert. Trailing tokens now fail validation so such text is wrapped as a JSON string.
- FIXED: `currentUserId()` helpers in 15 services (JournalService, FiscalPeriodService, ApService, ArService, ApprovalService, InventoryPostingService, StockAdjustmentService, GoodsReceiptService, PurchaseOrderService, PurchaseRequisitionService, FinalInspectionService, InspectionService, DispatchService, ReservationService, SalesOrderService) tested `instanceof iam.domain.User`, but the authenticated principal is `UserPermissionCache.CachedUser`, so every document they created, approved, posted, received, dispatched or inspected was attributed to user -1 and the ApprovalService requester/approver segregation check compared -1 with -1. They now read `CachedUser.id()`, the same mechanism as AuditService and JpaConfig; `UserAttributionIT` proves it. Rows written before this fix keep -1 and cannot be reattributed.

## R14 WMS (2026-10-03)
- Migration: `V27__wms.sql` (V26 was the HRM unrecorded-day setting); PLAN R14 says V25.
- A bin is backed by a `warehouse_locations` row (`warehouse_bins.location_id`, unique): the ledger keeps one location key and every existing posting, balance and reservation keeps working. Creating a bin creates its location (code = bin code, type from the zone: BULK -> RAW_MATERIAL, PICKING -> FINISHED, RECEIVING -> QUARANTINE, DISPATCH/STAGING -> DISPATCH, QC -> QUALITY_PENDING, overridable). Because the location code is unique per warehouse, bin codes are unique per warehouse (stricter than DESIGN, which has them unique per zone). A bin code and zone never change, because the code is also the location code.
- Zone types gained `STAGING` (DESIGN lists BULK, PICKING, RECEIVING, DISPATCH, QC): cross-dock needs somewhere to stage goods that is neither storage nor outbound. Bin columns `aisle`, `rack`, `level`, `bin_position` were added for the Warehouse -> Zone -> Aisle -> Rack -> Bin structure (WMS-001).
- Transfer-order lines carry `from_location_id`/`to_location_id` (the ledger keys) next to `from_bin_id`/`to_bin_id`, because stock received into a plain location (not a bin) can still be put away; `batch_id` is a material or finished-goods batch id according to `item_type`; `stock_status` is resolved at confirmation, not at planning. Header columns added: `wave_id`, `cross_dock_target_type/id`, `notes`; movement type `CROSS_DOCK` added.
- Only `TransferOrderService.confirm` moves stock, through `InventoryPostingService.transfer` (STOCK_TRANSFER, reference `TRANSFER_ORDER`). Confirmation locks the order row, so two concurrent confirmations move the stock once. A transfer preserves the stock status. `AccountingBridgeService` ignores STOCK_TRANSFER: a move between locations has no accounting effect (before this it logged a missing-assignment warning on every transfer). ArchUnit (`WmsArchTest`) enforces: WMS never touches the ledger tables, only `TransferOrderService` calls the posting service, cycle counts never post, WMS calls no procurement, sales or production service, and nothing outside WMS depends on WMS.
- Reads of stock for WMS go through `StockLocationQueryService` (inventory package, JDBC, read-only, flushes pending JPA writes first) so the existing rule "only posting and query services use InventoryBalanceRepository" still holds.
- Put-away (R14-2.2, R14-6.1) is planned AFTER_COMMIT of a goods receipt in its own transaction and never fails the receipt; `wms.putaway.auto_create` (default true) switches it off, and `POST /api/wms/transfer-orders/putaway/from-receipt/{id}` plans one by hand. Strategies per warehouse and material type (`putaway_strategy_rules`; a rule without a type is the warehouse default; `wms.putaway.default_strategy` applies when there is no rule): FIXED_BIN (item-to-bin assignment, falling back to nearest empty bin), NEAREST_EMPTY (first empty bin by zone then bin code that passes the capacity and material-type checks), BULK_FIRST (BULK-zone bin first, then nearest empty). Only BULK and PICKING zones hold stored stock. A line gets no destination when no bin qualifies; the operator picks one at confirmation. DESIGN 20.2 says "assign to available store operator": that is not automatic, orders are assigned by hand (`/assign`).
- Stock still awaiting inspection (material batch not AVAILABLE, finished-goods batch not APPROVED or PARTIALLY_APPROVED) may be moved only into QUARANTINE or QC bins or RECEIVING or QC zones: confirming such a put-away into storage is refused with PUTAWAY_BLOCKED until inspection accepts the batch (WMS-003: unloading, inspection, then put-away). The order itself is created at receipt so the task is visible.
- Bin capacity (decision #15): advisory by default; `wms.bin_capacity.enforce` (default false) rejects a breach with BIN_CAPACITY_EXCEEDED. Checked: weight (current weight of the stock at the bin location plus the incoming weight, against `max_weight_kg`) and allowed material types (`allowed_material_types`, case-insensitive list; products need PRODUCT or FINISHED_GOODS). Volume (`max_volume_m3`) is stored but NOT checked: the master data holds no item volumes. Item weight: product `unit_weight_kg`; a material counts only when its unit of measure is KG (1 kg per unit), otherwise 0. QUARANTINE and QC bins accept anything. The cached `current_weight_kg` is refreshed from the ledger after each confirmation. During planning a bin that would breach is skipped (except a fixed-bin assignment, which keeps the warning).
- Picking (R14-2.3): the existing dispatch is atomic (it posts SALES_DISPATCH when it is created), so there is no pre-dispatch state to hang a pick on. Picking orders are therefore planned when a SALES ORDER IS APPROVED (`SalesOrderApprovedEvent`, `wms.picking.auto_create`, default true) or on demand (`POST /api/wms/picking/sales-orders/{id}`); this is the reading of "dispatch triggers picking" that fits the implemented flow, and DispatchService is unchanged. One picking order per warehouse that holds approved stock (finished-goods status APPROVED); lines in first-in order (finished-goods batches have no expiry, so the oldest `produced_on` first), bin-mapped where possible; stock reserved for other orders is not offered; a shortage is noted on the order. A picking line without a destination bin is a verified pick: it records the pick (bin and batch scans) and posts nothing, because the dispatch posts the stock out; giving a destination (for example a DISPATCH staging bin) makes it a real transfer. Existing orders are returned, not duplicated.
- Waves (R14-6.2): `pick_waves` and `pick_wave_orders`; creating a wave plans (or attaches the existing) picking orders of its sales orders; an order can be in one open wave only; release makes it workable, cancel cancels its open orders, and the wave completes by itself when all its orders are closed. The consolidated pick list sums what is still to pick per bin, item and batch across the wave with a per-order breakdown, ordered zone then bin; `zoneId` limits it to one zone (zone-based picking).
- Cross-dock (R14-6.3, WMS-008): `POST /api/wms/transfer-orders/cross-dock` replaces the open put-away order of the receipt (one that has confirmed stock blocks it) with a CROSS_DOCK order to a staging bin: a STAGING-zone bin, or for a sales order a DISPATCH-zone bin; none configured is an error. The target production or sales order must exist.
- Cycle counts (R14-4.1): types ZONE (all stock in the bins of a zone), ABC (items of one class, classified from consumption value over `wms.cycle_count.abc_lookback_days`: A until the cumulative share reaches `wms.cycle_count.abc_a_pct`, B until `abc_b_pct`, otherwise C; items with no consumption are C; there is no ABC column on the item masters) and RANDOM (a random sample of stock lines). The count is blind while open (the API returns no system quantity or variance); review recomputes the system quantity from stock as it is now; posting raises one `StockAdjustmentService.request` per variance line, which follows the existing approval steps and Admin threshold, and never changes stock itself. Counts are by stock line (bin or location, item, batch, status).
- Permissions beyond the four in R14-5.2 (`BIN_MANAGE`, `PUTAWAY_MANAGE`, `PICKING_MANAGE`, `WAVE_MANAGE`): `WMS_VIEW` (read everything), `TRANSFER_MANAGE` (internal transfers) and `CYCLE_COUNT_MANAGE`. Executing an order (assign, start, confirm, cancel, set target) is admitted for any of PUTAWAY_MANAGE, PICKING_MANAGE or TRANSFER_MANAGE at the endpoint and the service then requires the one that owns the movement type (PUTAWAY and CROSS_DOCK -> PUTAWAY_MANAGE, PICKING -> PICKING_MANAGE, INTERNAL_TRANSFER -> TRANSFER_MANAGE). Roles: `WAREHOUSE_MANAGER` (new: all WMS permissions plus everything STORE_MANAGER has); STORE_MANAGER gets all WMS permissions; STORE_OPERATOR gets WMS_VIEW, PUTAWAY_MANAGE, PICKING_MANAGE and TRANSFER_MANAGE. No demo warehouse-manager user was created: there is still no demo-user mechanism.
- Document numbers follow the implemented format: transfer orders `TO/YY/NNNNN`, waves `WV/YY/NNNNN`, cycle counts `CC/YY/NNNNN`.
- Scanning: confirmation accepts the scanned bin and batch codes next to the quantity; a code that does not match the task is refused (SCAN_MISMATCH) before anything moves. A destination bin may also be identified by scanned code alone. There is no barcode or RFID hardware integration (REQUIREMENTS defers it).

## R15 PLM (2026-10-04)

- Lifecycle (PLM-005) lives in a new column `products.lifecycle_status` (DEVELOPMENT, PROTOTYPE, APPROVED, ACTIVE, PHASE_OUT, OBSOLETE), separate from `products.status` (DRAFT/ACTIVE/OBSOLETE master-data state). Existing and newly created products default to ACTIVE, so nothing about how they are ordered or produced changes.
- No ordering or production blocking for PHASE_OUT/OBSOLETE products. REQUIREMENTS PLM-001..005 specify none (PLM-005 only says transitions are audited), and CLAUDE.md says to enforce only what is specified. If wanted, it is a new rule with its own task, tests and a decision here.
- Lifecycle moves one step forward at a time, with a mandatory reason, and OBSOLETE is terminal (the spec lists a ladder and no way back). Each move writes a `product_lifecycle_events` row and a `PRODUCT_LIFECYCLE_CHANGE` audit entry (old value, new value, reason) in the same transaction. The service refuses skips, backward moves and a blank reason without leaving a trace.
- ECO approval creates nothing. `EcoService.implement` (decision #2) creates one DRAFT revision per BOM item by calling `BomService.copyRevision` on the product's ACTIVE BOM, links `old_bom_id`/`new_bom_id` on the item, and records a lifecycle event (from = to) for every affected product. It does not submit or activate the draft: the old BOM is superseded only when the engineer takes the new revision through DRAFT, ENGINEERING_REVIEW, APPROVED and ACTIVE (DESIGN section 21.2 step 2 is narrowed accordingly). The change description is stored in the revision's `change_reason`; the engineer edits the lines of the DRAFT with the normal BOM update because the ECO has no structured line-change format to apply.
- Implementation is all or nothing and runs under a row lock on the ECO. It fails with BOM_NOT_ACTIVE when an affected product has no ACTIVE BOM, and with ILLEGAL_STATE_TRANSITION when the product already has an open revision (DRAFT, ENGINEERING_REVIEW or APPROVED), which would otherwise collide on the revision letter. Either way no revision is left behind and the ECO stays APPROVED.
- Affected items of type ROUTING and PRODUCT are recorded and traced, but implementation takes no automatic action for them (routing changes are made in the routing editor). Every item references a product (`product_id NOT NULL`), unique per ECO and item type.
- IMPLEMENTING is entered and left inside the one implement transaction, so it is never persisted; it exists in the state machine as the plan specifies. A reviewer may return a REVIEW ECO to DRAFT (reason required); ECOs can be cancelled with a reason until they are implementing.
- Added columns beyond DESIGN: `ecos.reason` (PLM-002 asks for a reason) and `ecos.status_reason`; `product_lifecycle_events.reason` is NOT NULL.
- Permissions: the four in R15-3.2 (`ECO_CREATE`, `ECO_APPROVE`, `DRAWING_MANAGE`, `SPECIFICATION_MANAGE`) plus `PLM_VIEW` and `LIFECYCLE_MANAGE`. `DRAWING_MANAGE` already existed from V1 (granted to the engineering roles) and is only added to `PLM_ENGINEER`; `SPECIFICATION_MANAGE` is new. Both are for the document module (R17) and guard no R15 endpoint. `ECO_CREATE` covers create, edit, submit, implement and cancel; `ECO_APPROVE` covers approve, return and cancel. ECO_APPROVE goes to ADMIN and to every role that already holds BOM_APPROVE; there is no initiator/approver separation because the requirements do not ask for one.
- `PLM_ENGINEER` is seeded with the PLM permissions plus BOM_VIEW/CREATE/UPDATE and PRODUCT_VIEW. As in R12 to R14, no demo PLM user is created because there is no demo-user mechanism.
- API: `/api/ecos` (list, get, create, update, submit, return, approve, cancel, implement) per ARCHITECTURE section 12, and `/api/product-lifecycle` (list, get with history, transition). `BomService.copyRevision(id, changeReason)` is a new overload; the one-argument method is unchanged.
- The ECO item product picker reads `GET /api/product-lifecycle` (needs only PLM_VIEW) instead of `/api/products`. Found while building it: `ProductController` guards on `MASTER_PRODUCT_VIEW`/`MASTER_PRODUCT_MANAGE`, and no migration seeds those codes (V1 seeds `PRODUCT_VIEW`/`PRODUCT_CREATE`/`PRODUCT_UPDATE`), so real users cannot call the product master endpoints; `SearchIT` and the security tests pass only because they supply the authority themselves. Not changed in R15; needs its own fix. Fixed afterwards, see 'Permission alignment' below.
- Existing bug found and fixed by V28: V8 gave `bom.bom_number` its own UNIQUE constraint on top of `UNIQUE (bom_number, revision)`, so `BomService.copyRevision` (same number, next revision letter) failed on PostgreSQL with `bom_bom_number_key`; the BOM revision feature had never worked end to end. V28 drops the single-column constraint and the entity no longer declares it unique. Rule 4 note: V8 is untouched; the fix is the additive V28.
- Second existing bug found and fixed: `BomService.activate` superseded the previous ACTIVE BOM and activated the new one in the same flush, so Hibernate could send the new ACTIVE update first and trip `ux_bom_one_active`. The previous BOM is now flushed as SUPERSEDED before the new one becomes ACTIVE (it had only worked when no earlier ACTIVE BOM existed).

## Permission alignment (2026-10-04)

- Root cause: authorities reach a user only through `role_permissions` (UserPermissionCache and JwtAuthenticationFilter); there is no ADMIN or superuser bypass. 18 controller guards used codes that no migration ever seeded (MASTER_*_VIEW/MANAGE, MASTERDATA_VIEW, MASTER_DATA_MANAGE, IAM_USER_MANAGE, IAM_AUDIT_VIEW, GOODS_RECEIVE, MAINTENANCE_CREATE, SALES_MANAGE, SALES_APPROVE, ALERT_VIEW, ALERT_MANAGE), and `SystemSettingController` required a literal `ADMIN` authority. So no real user, ADMIN included, could call master data, user administration, settings, audit, alert, goods receipt, sales approval or maintenance create endpoints. Tests passed only because they supplied the authority by hand with `@WithMockUser`.
- Fix direction: DESIGN section 7.1 is the canonical catalogue and section 7.4 already shows `ProductController` on PRODUCT_VIEW/CREATE/UPDATE, so the controllers and frontend were renamed to the seeded codes; V1 was not touched. Mapping: MASTER_PRODUCT_VIEW to PRODUCT_VIEW (POST PRODUCT_CREATE, PUT/activate/DELETE PRODUCT_UPDATE); MASTER_MATERIAL_VIEW to MATERIAL_VIEW or MASTERDATA_MANAGE (writes MASTERDATA_MANAGE); MASTER_CUSTOMER_* to CUSTOMER_MANAGE (reads also MASTERDATA_MANAGE); MASTER_SUPPLIER_* to SUPPLIER_MANAGE (reads also MASTERDATA_MANAGE); MASTERDATA_VIEW on machines and operations to any of the manage code, MASTERDATA_MANAGE and the production, maintenance or routing view codes; MASTER_DATA_MANAGE to REJECTION_REASON_MANAGE; IAM_USER_MANAGE to USER_VIEW/USER_CREATE/USER_UPDATE/USER_DELETE per verb, ROLE_MANAGE for role assignment and role listing, SETTINGS_MANAGE for settings; IAM_AUDIT_VIEW to AUDIT_VIEW; GOODS_RECEIVE to INVENTORY_RECEIVE; MAINTENANCE_CREATE to MAINTENANCE_MANAGE; SALES_MANAGE to SALES_UPDATE on orders and customer specs, RESERVE_FG on reservations, and removed from dispatch so sales staff cannot post dispatch stock movements.
- V29 seeds the three codes with no catalogue equivalent: ALERT_VIEW, ALERT_MANAGE, SALES_APPROVE. Grants are the narrowest sensible ones and need business review: ALERT_VIEW to ADMIN, PRODUCTION_MANAGER, QUALITY_MANAGER, STORE_MANAGER, PURCHASE_MANAGER, MANAGEMENT; ALERT_MANAGE to the same without MANAGEMENT; SALES_APPROVE to ADMIN only (the SALES role cannot approve its own orders until a sales-manager role is defined).
- Dead `'ADMIN'` alternatives in `hasAnyAuthority('X','ADMIN')` (dashboard, reports, traceability, maintenance) were removed; no user ever held an authority called ADMIN, so behaviour is unchanged.
- Frontend gates used three names that exist nowhere: ROUTING_VIEW (now PRODUCT_VIEW, matching the routing GET), BOM_MANAGE (BOM_CREATE for new, submit and recall, BOM_UPDATE for copy revision, matching BomController), PRODUCTION_MANAGE (PRODUCTION_UPDATE for cancel).
- Regression guards: `PermissionCatalogueIT` scans every handler method's `@PreAuthorize` and fails when a required authority is missing from the `permissions` table or is granted to no role. `RoleAccessIT` creates one real user per seeded role, logs in through `/api/auth/login` and probes representative endpoints for both access and 403, with nothing supplied by hand.
- Not changed, noted for review: creating a user with roles needs only USER_CREATE, so a future user-admin role holding USER_CREATE but not ROLE_MANAGE could grant any role at creation time; only ADMIN holds these today. Rows written before this change are unaffected because no permission data changed except the three additions.

## R16 Advanced Quality (2026-10-04)

- Migration is V30 (DESIGN section 22 said V27; V27 to V29 were WMS, PLM and the permission alignment). It creates `spc_control_charts`, `spc_data_points`, `capa_records`, `customer_complaints` and `first_article_inspections`, adds `SPC_OUT_OF_CONTROL` to the alert-type check, adds `FAI` to the inspection-type check on `quality_inspections`, and seeds four permissions and two settings. DESIGN section 22.4 lists the differences from the section 22 DDL.
- Chart types are `XBAR_R`, `P` and `C` (QMS-007 asks for X-bar, R, P and C). DESIGN also listed `XBAR_S`, `NP` and `U`; they are not implemented, so the check constraint does not allow them. Subgroup size is 2 to 10 for X-bar/R (Shewhart constants A2, D3, D4 are tabulated for exactly that range); P and C charts store 1.
- Control limits are established once, automatically, when a chart has collected `spc.min_subgroups_for_limits` plotted points (default 20; a plotted point is a completed subgroup for X-bar/R and every observation for P and C). From then on they are fixed, so a later outlier cannot widen the limits that judge it; `POST /api/spc/charts/{id}/recalculate-limits` (SPC_MANAGE, audited) recomputes them from all data and re-judges every point without raising new alerts.
- Out-of-control rules: Nelson rule 1 (a plotted statistic strictly beyond UCL or LCL) and rule 2 (`spc.nelson_rule2_run_length`, default 9, consecutive points strictly on one side of the centre line), plus `RANGE_R1` for the range chart. A violation sets `out_of_control` and `violation_rule` on the point and raises one `SPC_OUT_OF_CONTROL` alert per chart (an open alert is refreshed, not duplicated). P chart limits are drawn per point from its own sample size; the chart-level UCL/LCL on a P chart are for the average sample size.
- Capability uses the overall sample standard deviation (n - 1) of all measurements in the period, as DESIGN 22.2 says, not the within-subgroup estimate R-bar/d2. Cp needs both spec limits; with one limit only the one-sided index and Cpk are returned. All SPC arithmetic is BigDecimal (CLAUDE.md rule 8), stored at 6 decimal places.
- Inspections feed charts after the inspection commits (`@TransactionalEventListener(AFTER_COMMIT)`, new transaction, never fails the inspection, errors are logged). A chart is fed when the inspection's product (from its FG batch, else its production order) and a parameter name match: X-bar/R charts take the measured value, P and C charts take the inspection's rejected quantity as the defect count and accepted plus rejected as the sample size, only when both are whole numbers. One point per (chart, inspection), so resubmitting results is harmless. Incoming inspections have no product and feed nothing.
- CAPA state machine: OPEN, ROOT_CAUSE_ANALYSIS, ACTION_IN_PROGRESS, VERIFICATION, CLOSED, with VERIFICATION back to ACTION_IN_PROGRESS when verification fails (reason required). Moving to action needs a root cause, moving to verification needs a corrective action, and closing is its own action (`CAPA_CLOSE`, notes required, records `verified_by`). There is no rule that the verifier differs from the assignee because the requirements do not ask for one. One open CAPA per source record is allowed. A CAPA for a complaint can only be raised with the from-complaint action so `customer_complaints.capa_id` stays in step. The "evidence upload reference" in R16-2.2 is not built: it needs the document module (R17) and DESIGN has no column for it.
- Complaints: OPEN, IN_PROGRESS, RESOLVED, CLOSED (a resolved complaint can reopen). Resolving needs a disposition and notes. `category` is added to the DESIGN table so the complaint report can group by reason. The quantity returned is recorded only; no stock is posted (the existing `CUSTOMER_RETURN` flow is untouched). The FG batch link drives the trace view through `TraceabilityService.traceFgBatch`. The complaint report is `QUAL_COMPLAINTS` (RPT-004), requiring `QUALITY_VIEW`.
- Quality staff cannot read the customer master, so the complaint form uses `GET /api/complaints/lookups/customers` (COMPLAINT_MANAGE) instead of widening a role.
- FAI: required automatically when an ECO is implemented (one per affected product) and when a product is first moved to the APPROVED lifecycle state, or raised by hand. At most one open FAI per product (partial unique index), so the triggers are idempotent. Starting it links the product's active FINAL inspection plan (else IN_PROCESS) and the first production order and creates an inspection of the new type `FAI` (one article, items from the plan). Measured values go through `POST /api/fai/{id}/results`; the quality service marks the article accepted when no item failed. Completing closes that inspection (APPROVED or REJECTED) and sets the FAI PASSED or FAILED; a failed FAI is repeated as a new one. The generic inspection accept and reject refuse FAI inspections.
- The FAI report is a print-friendly page, not a generated PDF: the project has no PDF library (same trade as the payroll slips in R13). `GET /api/fai/{id}/report` returns the data.
- The triggers are common events (`EcoImplementedEvent`, `ProductLifecycleChangedEvent`, `InspectionResultsSubmittedEvent` in `common.event`), because the PLM ArchUnit rule forbids anything outside `plm` depending on it. `QualityPlusArchTest` also forbids stock, finance and inspection-status writes from the new package.
- Permissions: new `SPC_MANAGE`, `CAPA_MANAGE`, `CAPA_CLOSE`, `COMPLAINT_MANAGE`, granted to ADMIN and QUALITY_MANAGER only (REQUIREMENTS names no role). Reads use `QUALITY_VIEW` (ADMIN, QUALITY_MANAGER, MANAGEMENT), SPC data entry and starting an FAI use `QUALITY_INSPECT`, completing an FAI uses `QUALITY_APPROVE`. SALES cannot register complaints under this grant; review whether customer-facing staff should hold `COMPLAINT_MANAGE`. No demo quality-engineer user, as in R12 to R15.
- Frontend draws control charts as inline SVG (the PLAN named Chart.js; no new dependency was added). Product pickers use `/api/products` (needs `PRODUCT_VIEW`, which QUALITY_MANAGER holds) because quality roles do not hold `PLM_VIEW`.
- Gap found: no screen anywhere submitted inspection results (the existing inspection list only accepts or rejects). The FAI screen is the first with a value-entry form; incoming, in-process and final inspections still enter results through the API only.
- FIXED (2026-10-04): `GET /api/audit-logs` (and `/export`), `GET /api/inventory/ledger`, `GET /api/sales/orders` and `GET /api/sales/dispatches` with a one-sided date filter returned 500 on PostgreSQL ("could not determine data type of parameter"): `:from IS NULL OR col >= :from` binds an untyped null for `Instant` and `LocalDate`. Equality filters on `Long`/`String`/`Boolean`/enum parameters (`:x IS NULL OR col = :x`) work and are unchanged. ## R17 Documents and Notifications (2026-10-04)

- Migration is V31 (DESIGN section 23 had no number; V28 PLM, V29 permission alignment, V30 advanced quality were taken). It creates `document_categories`, `documents`, `document_versions`, `document_links`, `notification_templates`, `notification_subscriptions` and `notifications`, five permissions, five settings and the templates. Every table has the DESIGN 1.1 standard columns.
- Deviation from DESIGN 23.1: the file facts (storage key, size, checksum, type) are on `document_versions` and the record link on `document_links`, so a document has a version history (drawing revisions, PLAN R17-3.2) and can be attached to several records. `documents.version` (DESIGN's label) is `current_version_no`, because `version` is the optimistic-lock column. `file_reference` is the per-version `storage_key`.
- PLAN and REQUIREMENTS say "file references, content stored externally". Read as "outside the database": the content is stored by the service behind a `DocumentStorage` interface. The only implementation writes under `DOCUMENTS_STORAGE_ROOT` (a volume in the compose files); an S3-style store replaces it without touching `DocumentService`. ArchUnit keeps the storage package private to the document service.
- Upload safety: extension allowlist (setting `documents.allowed_extensions`), a content-signature check for PDF/PNG/JPEG/GIF/Office files, a server-chosen MIME type (the client's is never trusted), size limit (setting `documents.max_size_mb`, default 25, enforced while streaming; the container limit is 50 MB), SHA-256 recorded per version, server-generated storage keys (`yyyy/MM/uuid`, validated against that exact shape and re-checked to resolve inside the root), sanitised display filenames, `Content-Disposition: attachment` plus `nosniff` on every download. A rolled-back upload deletes its file. No virus-scan hook: REQUIREMENTS does not list one.
- Access: DOCUMENT_VIEW to read, DOCUMENT_UPLOAD to upload, version, link and submit, DOCUMENT_APPROVE to approve, return or obsolete, DOCUMENT_MANAGE for categories and for reading every document. A document linked to records is readable only by someone who may read at least one of them (the authorities mirror each record's own read endpoint: PRODUCT_VIEW, BOM_VIEW, PLM_VIEW, SUPPLIER_MANAGE/MASTERDATA_MANAGE, MACHINE_MANAGE/MASTERDATA_MANAGE/PRODUCTION_VIEW/MAINTENANCE_VIEW, QUALITY_VIEW/CAPA_MANAGE, QUALITY_VIEW/COMPLAINT_MANAGE); an unlinked document (an SOP) is readable by every DOCUMENT_VIEW holder. Linking needs read access to that kind of record. A category may demand an extra authority: DRAWING needs DRAWING_MANAGE and SPECIFICATION needs SPECIFICATION_MANAGE (PLAN R17-3.2), for upload, new versions and link changes.
- State machine: DRAFT -> REVIEW -> APPROVED -> OBSOLETE, REVIEW -> DRAFT (reason mandatory), DRAFT -> OBSOLETE. The approver may not be the uploader of the current version (SEGREGATION_OF_DUTIES, as for purchase orders). A new version of a document in REVIEW or APPROVED returns it to DRAFT (and clears the approval) so a changed file is never shown as approved. An OBSOLETE document takes no new versions. Documents are never deleted; obsolescence is the end of life. `retention_years` is recorded but nothing enforces it yet.
- Every upload, new version, link, unlink, state change and download writes an audit entry; a download that fails because the file is missing is not audited as a download.
- Notifications: one `notifications` row per recipient and channel. IN_APP rows are SENT immediately. EMAIL rows are the outbox: PENDING until the delivery job (`NotificationOutboxJob`, ShedLock, every 30 s, `ims.notification.outbox-delay-ms`) sends them. Delivery is one transaction per message under a row lock; a failure stores a one-line error (class and first message line, bounded, never a stack trace or credentials), schedules a retry after `notification.email.retry_base_seconds` doubling per attempt (capped at one hour) and ends in FAILED after `notification.email.max_attempts`. Delivery is at-least-once: a crash between the SMTP accept and the commit sends the message again.
- The recipient may be an external address (a supplier contact): `user_id` is then NULL and `recipient_email` is set (DESIGN made `user_id` NOT NULL). `dedup_key` (unique) makes a replayed event idempotent per recipient and channel.
- Notifications never block the business transaction: listeners run AFTER_COMMIT (with `fallbackExecution`), call `NotificationService` (REQUIRES_NEW, because joining the finished transaction would silently lose the rows) and swallow their own failures. A failing notification insert cannot roll back its caller (tested).
- Templates are a Mustache subset implemented in `TemplateRenderer` (`{{name}}` and dotted paths into nested maps; missing values render empty; no sections, partials or evaluation, so a template can only read the payload it is given). It avoids a dependency; subjects have line breaks collapsed. DESIGN said "Mustache template engine".
- Preferences: `notification_subscriptions` has an `enabled` flag. Without a row every channel a template allows is on; a row overrides it, so unsubscribing is `enabled = false`. A user can only set channels the template uses.
- Events wired: every new alert (published by the `Alert` entity itself, so all four code paths that create alerts are covered; repeat sightings of an open alert do not notify again) goes in-app to every ALERT_VIEW holder and by e-mail only at or above `notification.alert.email_min_severity` (default HIGH); a type with its own template uses it (switching that template off silences the type), a type without one uses `ALERT_GENERIC`. PO approval e-mails the supplier contact (when the supplier has an address) and notifies who submitted the PO in-app (PLAN R17-3.1 says "approved"; if suppliers should only hear once the PO is sent, change the trigger to `sendToSupplier`). A CAPA gaining an assignee notifies them in-app (no dedup, so a hand-back to a previous assignee still notifies; assigning to yourself needs no notice).
- PLAN R17-2.3 says "replace alert email with NotificationService": the code base had no alert e-mail (the only mail sent was the password reset in `AuthService`, which is unchanged). Alerts now have an e-mail channel through the engine.
- CAPA evidence (deferred from R16): documents link to a CAPA (`entity_type CAPA`), the seeded category `CAPA_EVIDENCE` and the attachments widget on the CAPA screen. Closing a CAPA does not require evidence; REQUIREMENTS does not ask for it.
- Permissions needing business review: DOCUMENT_VIEW goes to ADMIN, ENGINEER, PLM_ENGINEER, PRODUCTION_MANAGER, SUPERVISOR, QUALITY_MANAGER, STORE_MANAGER, PURCHASE_MANAGER, MAINTENANCE and MANAGEMENT (not OPERATOR, SALES, DISPATCH, STORE_OPERATOR); DOCUMENT_UPLOAD to ADMIN, ENGINEER, PLM_ENGINEER, PRODUCTION_MANAGER, QUALITY_MANAGER, PURCHASE_MANAGER and MAINTENANCE; DOCUMENT_APPROVE to ADMIN, PRODUCTION_MANAGER and QUALITY_MANAGER; DOCUMENT_MANAGE and NOTIFICATION_MANAGE to ADMIN only. REQUIREMENTS names no roles for documents. A user's own inbox and preferences need only a signed-in user (`isAuthenticated()`), so there is no permission to seed for them.
- Frontend: documents list, upload, detail (versions, links, state actions) and an attachments widget used on the ECO and CAPA screens and, in a dialog, on the product and BOM lists; the toolbar bell polls the unread count every minute; inbox, preferences and an administrator screen for templates and the delivery log.
- Not done: `docker/.env.example` was not updated (the release agent may not edit that file); the new variables are documented in docs/RUNBOOK.md. No demo user for the new permissions (no demo-user mechanism). Document search is by number and title only (no full-text search of content).
- Noticed outside R17, not changed: the frontend route guard for `admin/settings` still requires a literal `ADMIN` permission code, which no user holds (the backend requires SETTINGS_MANAGE); the permission audit changed the controller but this route guard remains.
