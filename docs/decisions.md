## R12 CRM (2026-10-03)
- Migration number: CRM is `V23__crm.sql` (V22 was taken by MRP); PLAN R12-1.1/1.2 say V22.
- Permissions: besides the four in R12-3.3 (`LEAD_MANAGE`, `OPPORTUNITY_MANAGE`, `QUOTATION_CREATE`, `CUSTOMER_ACTIVITY`) there is `CRM_VIEW` (read everything), `PRICE_LIST_MANAGE` and `CUSTOMER_TAG_MANAGE`. Each endpoint declares one authority. `CRM_AGENT` gets the four plus `CRM_VIEW`, `SALES_VIEW`, `PRODUCT_VIEW` (needed for the product picker), `REPORT_VIEW`, `DASHBOARD_VIEW`; `SALES` gets `CRM_VIEW` + price and tag management; `ADMIN` gets all seven. No demo CRM user is created (no demo-user mechanism, as for CONTROLLER and PLANNER).
- Lead machine is strict: NEW -> CONTACTED -> QUALIFIED -> CONVERTED; UNQUALIFIED from any open state with a mandatory reason (`disqualify_reason` column added to DESIGN 18.1). Converted/unqualified leads are terminal and not editable. Endpoints are per transition (`/contact`, `/qualify`, `/disqualify`, `/convert-to-opportunity`), never a free-form status update.
- Lead conversion creates a customer (code `CUS/YY/NNNNN` from DocumentNumberService, name and contact details from the lead) unless an existing customer id is given, opens a PROSPECT opportunity inheriting contact, value, close date and owner, links the contact to the customer, and moves activity logged against the lead into the customer's log.
- Opportunity machine is forward-only: PROSPECT -> QUALIFIED -> PROPOSAL -> NEGOTIATION -> CLOSED_WON, CLOSED_LOST from any open stage with a mandatory reason. The stage sets the probability (10/25/50/75/100/0). Converting a quotation links it (`converted_quotation_id`) and closes the opportunity as WON when it is in PROPOSAL or NEGOTIATION; earlier stages are linked but left open. The board moves cards with buttons, not drag and drop.
- Quotation: DRAFT -> SENT -> ACCEPTED -> CONVERTED, SENT -> REJECTED (reason), DRAFT/SENT -> EXPIRED (daily sweep 01:15 and a check on accept). Columns added to DESIGN 18.1: `payment_terms`, `notes`, `sent_at`, `responded_at`, `reject_reason`. Default validity is setting `crm.quotation.default_validity_days` (30). The net unit price is `unit_price x (100 - discount) / 100` rounded half-up to 4 places and the line total is quantity x that net price, so the sales order created on conversion (which stores only the net unit price) totals exactly the quotation.
- Conversion needs `QUOTATION_CREATE` and creates a DRAFT sales order through `SalesOrderService` (approval still needs `SALES_APPROVE`); CRM never touches sales entities or repositories directly (ArchUnit).
- Pricing (R12-4.1): one table `customer_prices` instead of `price_lists` + `customer_prices`; a null `customer_id` is the standard price. Precedence among rows valid on the date and reachable by quantity: customer-specific beats standard, then the highest `min_qty`, then the latest `valid_from`. A quotation line with no explicit price and no price list row is rejected.
- Segmentation (R12-4.2): `customer_tags` (group INDUSTRY/REGION/TIER/STRATEGIC/OTHER + name) and `customer_tag_assignments`; `GET /api/crm/customers?tagId=` lists customers with their tags. The partner module's customer API is untouched.
- Activities store the customer on every row, derived from the contact, opportunity or lead when not given; at least one of customer, contact, lead or opportunity is required (DB check). Contacts are deactivated, never deleted.
- Pipeline report (R12-4.3) `CRM_PIPELINE` is in the report catalogue (authority `CRM_VIEW`). CSV export is done in the browser; XLSX and PDF export are NOT implemented because the platform has no report export infrastructure yet - do that once for every report rather than per module.
- FIXED (2026-10-03): `@Query` searches written as `(:q IS NULL OR LOWER(x) LIKE LOWER(CONCAT('%', :q, '%')))` failed on PostgreSQL with `function lower(bytea) does not exist` when `q` was null, so list endpoints without a search term returned 500. Affected `CustomerRepository`, `SupplierRepository`, `MaterialRepository`, `ProductRepository`, `UserRepository` and `WarehouseRepository`. Pattern now in force: the query uses `(:q = '' OR ...)` and each repository exposes a default `search(...)` that normalises null/blank to "" via `common.search.SearchText.normalise`, so callers and API behaviour are unchanged. Covered by `SearchIT` (absent, blank, whitespace, matching and non-matching q on every list endpoint). New text-search queries must follow the same pattern (CRM's Specification-based and `:q = ''` searches already did).

- Migrations: HRM core is `V24__hrm_core.sql` and payroll is `V25__payroll.sql` (V23 was taken by CRM); PLAN R13 says V23/V24.
- Permissions: besides `EMPLOYEE_MANAGE`, `PAYROLL_RUN`, `ATTENDANCE_MANAGE` and `LEAVE_APPROVE` (R13-5.2) there are `HR_VIEW` (read employees without pay data, skills, attendance, leave, training) and `LEAVE_APPLY` (self-service; granted to every role so any employee can apply for their own leave). `HR_VIEW` is also granted to PRODUCTION_MANAGER and SUPERVISOR so planning can see who is authorised on a machine. The `HR_MANAGER` role is seeded; as for CONTROLLER and PLANNER no demo user is created because the repository has no demo-user mechanism.
- Pay and bank data (`basicPay`, allowances, bank, PF/ESI numbers) is returned only to callers holding `EMPLOYEE_MANAGE` or `PAYROLL_RUN`; everyone else gets `compensationVisible=false` and nulls. Every payroll endpoint, including reads of runs and slips, needs `PAYROLL_RUN`. Changing basic pay or fixed allowances requires a reason and writes `EMPLOYEE_PAY_CHANGE` to the audit log with the old and new figures.
- Columns added to DESIGN section 19.1: `employees.date_of_leaving`, `fixed_travel_allowance`, `fixed_other_allowances`, `default_shift` (DESIGN's slip has travel and other allowances but the employee had nowhere to hold them); `attendance.source` (MANUAL or AUTO); `leave_types.paid` and `max_carry_forward_days`; `leave_applications.half_day`, `decided_by`, `decided_at`, `decision_reason` (replacing DESIGN's `approved_by`/`approved_at`, because rejection and cancellation are decisions too); `payroll_slips.da` and `cost_centre_id`; `payroll_runs.approved_by`, `paid_at`, `paid_by`, `payment_journal_header_id`. New tables: `shifts` (R13-2.1), `leave_balances` (ARCHITECTURE section 19), `training_records` (DESIGN names it but defines no columns; shaped from HRM-006).
- Payroll run states are DRAFT -> COMPLETED (approved, journal posted) -> PAID. DESIGN's PROCESSING value stays legal in the database but is never entered because slip calculation is synchronous.
- Attendance rules: a working day is any day that is not a weekly off (`hrm.weekly_off_days`, default SUNDAY) and not recorded HOLIDAY for that employee. Unrecorded days are governed by `hrm.payroll.unrecorded_day_policy` (V26): ABSENT (default) makes a working day with no attendance row and no approved leave loss of pay; PRESENT keeps the original behaviour where only explicit ABSENT (1 day), HALF_DAY (0.5) and unpaid-leave days reduce pay. Weekly offs, HOLIDAY days and approved paid leave (including paid half-day leave) are never penalised, and days from today onward are never penalised, so a mid-month run does not dock the rest of the month. The policy that applied is written into the PAYROLL_CALCULATE audit entry. Approved leave overrides an absence on the same day. There is no holiday calendar table; HR marks HOLIDAY through the bulk attendance endpoint.
- Pay proration: factor = paid days / working days in the month; joiners are paid from the joining date and leavers to the leaving date (the days outside employment count as loss of pay on the slip). Basic, HRA, DA and the fixed allowances all prorate. Amounts round HALF_UP to 2 decimals, day counts to 1.
- Statutory figures are `system_settings` rows (`hrm.payroll.*`), never code. Seeded defaults: HRA 40%, DA 0%, PF 12% + 12% on basic capped at 15,000, ESI 0.75% + 3.25% when gross <= 21,000, professional tax slabs `7500:0,10000:175,:200`, and simplified TDS (projected full-month gross x 12, less a 75,000 standard deduction, new-regime slabs `300000:0,700000:5,1000000:10,1200000:15,1500000:20,:30`, 1,200,000 rebate limit, 4% cess, spread over 12 months). HR and finance must review these every financial year; the PT slab is a Maharashtra-style placeholder. A calculation that would produce a negative net pay aborts the run and names the employee.
- Payroll journal: approval posts one balanced journal through the new `JournalService.postSourceJournal` (same transaction as the run, unlike `postAutoJournal` which is REQUIRES_NEW for AFTER_COMMIT listeners): Dr 5201 Salary Expense, 5205 Employer PF, 5206 Employer ESI (per cost centre of the employee), Cr 2501 Salary Payable (net), 2502 PF Payable, 2503 ESI Payable, 2504 Professional Tax Payable, 2505 TDS Payable. Posting date is the last day of the payroll month, so that fiscal period must be OPEN at initiate, calculate and approve (rule 14). Marking the run paid posts Dr 2501 / Cr 1201 Main Bank on the chosen payment date. HRM reaches finance only through JournalService (ArchUnit).
- Approval freezes the month: attendance and leave changes for a month with a COMPLETED or PAID run are refused (`PAYROLL_LOCKED`), including auto-capture.
- Leave: balances are per employee, leave type and calendar year of the application's first day; the row is created on first use with the type's entitlement and a carry-forward capped at `max_carry_forward_days`. No pro-rata entitlement for mid-year joiners. Unpaid types (LOP) and types without a yearly maximum carry no balance. Pending requests do not reserve balance; it is checked again on approval. Nobody approves their own leave (`SEGREGATION_OF_DUTIES`). Approving writes LEAVE attendance rows for working days that have no record; cancelling an approved leave removes them and restores the balance.
- Attendance auto-capture (HRM-002): the production service publishes `OperationStartedEvent` and `OperationCompletedEvent`; an AFTER_COMMIT listener in HRM sets check-in (earliest start) and check-out (latest completion) for the employee linked to the operator, in its own transaction and never failing the operation. The operator is the operation's assigned operator, else the user who acted. Holiday, leave and half-day records are left for HR.
- Skill matrix (HRM-005): `GET /api/hrm/skills/authorised?machineId=&operationId=` lists active employees with a non-expired authorisation; R18 scheduling will call it. `GET /api/hrm/employees/unlinked-users` lists OPERATOR and SUPERVISOR users with no employee record (MDM-041).
- Pay slips: the project has no PDF library, so the slip is a print-friendly page and "download" is the browser's print / save as PDF.
- Run numbers `PAY/YY/NNNNN`, leave `LV/YY/NNNNN`, employees `EMP/YY/NNNNN` follow the implemented document-number format.
- FIXED: `AuditService.asJson` let text that merely begins with a number or literal (for example `2 slips; gross ...`) through as "valid JSON" because Jackson ignores trailing tokens; PostgreSQL then rejected the JSONB insert. Trailing tokens now fail validation so such text is wrapped as a JSON string.
- FIXED: `currentUserId()` helpers in 15 services (JournalService, FiscalPeriodService, ApService, ArService, ApprovalService, InventoryPostingService, StockAdjustmentService, GoodsReceiptService, PurchaseOrderService, PurchaseRequisitionService, FinalInspectionService, InspectionService, DispatchService, ReservationService, SalesOrderService) tested `instanceof iam.domain.User`, but the authenticated principal is `UserPermissionCache.CachedUser`, so every document they created, approved, posted, received, dispatched or inspected was attributed to user -1 and the ApprovalService requester/approver segregation check compared -1 with -1. They now read `CachedUser.id()`, the same mechanism as AuditService and JpaConfig; `UserAttributionIT` proves it. Rows written before this fix keep -1 and cannot be reattributed.

## R14 WMS (2026-10-03)
- Migration: `V27__wms.sql` (V26 was the HRM unrecorded-day setting); PLAN R14 says V25.
- A bin is backed by a `warehouse_locations` row (`warehouse_bins.location_id`, unique): the ledger keeps one location key and every existing posting, balance and reservation keeps working. Creating a bin creates its location (code = bin code, type from the zone: BULK -> RAW_MATERIAL, PICKING -> FINISHED, RECEIVING -> QUARANTINE, DISPATCH/STAGING -> DISPATCH, QC -> QUALITY_PENDING, overridable). Because the location code is unique per warehouse, bin codes are unique per warehouse (stricter than DESIGN, which has them unique per zone). A bin code and zone never change, because the code is also the location code.
- Zone types gained `STAGING` (DESIGN lists BULK, PICKING, RECEIVING, DISPATCH, QC): cross-dock needs somewhere to stage goods that is neither storage nor outbound. Bin columns `aisle`, `rack`, `level`, `bin_position` were added for the Warehouse -> Zone -> Aisle -> Rack -> Bin structure (WMS-001).
- Transfer-order lines carry `from_location_id`/`to_location_id` (the ledger keys) next to `from_bin_id`/`to_bin_id`, because stock received into a plain location (not a bin) can still be put away; `batch_id` is a material or finished-goods batch id according to `item_type`; `stock_status` is resolved at confirmation, not at planning. Header columns added: `wave_id`, `cross_dock_target_type/id`, `notes`; movement type `CROSS_DOCK` added.
- Only `TransferOrderService.confirm` moves stock, through `InventoryPostingService.transfer` (STOCK_TRANSFER, reference `TRANSFER_ORDER`). Confirmation locks the order row, so two concurrent confirmations move the stock once. A transfer preserves the stock status. `AccountingBridgeService` ignores STOCK_TRANSFER: a move between locations has no accounting effect (before this it logged a missing-assignment warning on every transfer). ArchUnit (`WmsArchTest`) enforces: WMS never touches the ledger tables, only `TransferOrderService` calls the posting service, cycle counts never post, WMS calls no procurement, sales or production service, and nothing outside WMS depends on WMS.
- Reads of stock for WMS go through `StockLocationQueryService` (inventory package, JDBC, read-only, flushes pending JPA writes first) so the existing rule "only posting and query services use InventoryBalanceRepository" still holds.
- Put-away (R14-2.2, R14-6.1) is planned AFTER_COMMIT of a goods receipt in its own transaction and never fails the receipt; `wms.putaway.auto_create` (default true) switches it off, and `POST /api/wms/transfer-orders/putaway/from-receipt/{id}` plans one by hand. Strategies per warehouse and material type (`putaway_strategy_rules`; a rule without a type is the warehouse default; `wms.putaway.default_strategy` applies when there is no rule): FIXED_BIN (item-to-bin assignment, falling back to nearest empty bin), NEAREST_EMPTY (first empty bin by zone then bin code that passes the capacity and material-type checks), BULK_FIRST (BULK-zone bin first, then nearest empty). Only BULK and PICKING zones hold stored stock. A line gets no destination when no bin qualifies; the operator picks one at confirmation. DESIGN 20.2 says "assign to available store operator": that is not automatic, orders are assigned by hand (`/assign`).
- Stock still awaiting inspection (material batch not AVAILABLE, finished-goods batch not APPROVED or PARTIALLY_APPROVED) may be moved only into QUARANTINE or QC bins or RECEIVING or QC zones: confirming such a put-away into storage is refused with PUTAWAY_BLOCKED until inspection accepts the batch (WMS-003: unloading, inspection, then put-away). The order itself is created at receipt so the task is visible.
- Bin capacity (decision #15): advisory by default; `wms.bin_capacity.enforce` (default false) rejects a breach with BIN_CAPACITY_EXCEEDED. Checked: weight (current weight of the stock at the bin location plus the incoming weight, against `max_weight_kg`) and allowed material types (`allowed_material_types`, case-insensitive list; products need PRODUCT or FINISHED_GOODS). Volume (`max_volume_m3`) is stored but NOT checked: the master data holds no item volumes. Item weight: product `unit_weight_kg`; a material counts only when its unit of measure is KG (1 kg per unit), otherwise 0. QUARANTINE and QC bins accept anything. The cached `current_weight_kg` is refreshed from the ledger after each confirmation. During planning a bin that would breach is skipped (except a fixed-bin assignment, which keeps the warning).
- Picking (R14-2.3): the existing dispatch is atomic (it posts SALES_DISPATCH when it is created), so there is no pre-dispatch state to hang a pick on. Picking orders are therefore planned when a SALES ORDER IS APPROVED (`SalesOrderApprovedEvent`, `wms.picking.auto_create`, default true) or on demand (`POST /api/wms/picking/sales-orders/{id}`); this is the reading of "dispatch triggers picking" that fits the implemented flow, and DispatchService is unchanged. One picking order per warehouse that holds approved stock (finished-goods status APPROVED); lines in first-in order (finished-goods batches have no expiry, so the oldest `produced_on` first), bin-mapped where possible; stock reserved for other orders is not offered; a shortage is noted on the order. A picking line without a destination bin is a verified pick: it records the pick (bin and batch scans) and posts nothing, because the dispatch posts the stock out; giving a destination (for example a DISPATCH staging bin) makes it a real transfer. Existing orders are returned, not duplicated.
- Waves (R14-6.2): `pick_waves` and `pick_wave_orders`; creating a wave plans (or attaches the existing) picking orders of its sales orders; an order can be in one open wave only; release makes it workable, cancel cancels its open orders, and the wave completes by itself when all its orders are closed. The consolidated pick list sums what is still to pick per bin, item and batch across the wave with a per-order breakdown, ordered zone then bin; `zoneId` limits it to one zone (zone-based picking).
- Cross-dock (R14-6.3, WMS-008): `POST /api/wms/transfer-orders/cross-dock` replaces the open put-away order of the receipt (one that has confirmed stock blocks it) with a CROSS_DOCK order to a staging bin: a STAGING-zone bin, or for a sales order a DISPATCH-zone bin; none configured is an error. The target production or sales order must exist.
- Cycle counts (R14-4.1): types ZONE (all stock in the bins of a zone), ABC (items of one class, classified from consumption value over `wms.cycle_count.abc_lookback_days`: A until the cumulative share reaches `wms.cycle_count.abc_a_pct`, B until `abc_b_pct`, otherwise C; items with no consumption are C; there is no ABC column on the item masters) and RANDOM (a random sample of stock lines). The count is blind while open (the API returns no system quantity or variance); review recomputes the system quantity from stock as it is now; posting raises one `StockAdjustmentService.request` per variance line, which follows the existing approval steps and Admin threshold, and never changes stock itself. Counts are by stock line (bin or location, item, batch, status).
- Permissions beyond the four in R14-5.2 (`BIN_MANAGE`, `PUTAWAY_MANAGE`, `PICKING_MANAGE`, `WAVE_MANAGE`): `WMS_VIEW` (read everything), `TRANSFER_MANAGE` (internal transfers) and `CYCLE_COUNT_MANAGE`. Executing an order (assign, start, confirm, cancel, set target) is admitted for any of PUTAWAY_MANAGE, PICKING_MANAGE or TRANSFER_MANAGE at the endpoint and the service then requires the one that owns the movement type (PUTAWAY and CROSS_DOCK -> PUTAWAY_MANAGE, PICKING -> PICKING_MANAGE, INTERNAL_TRANSFER -> TRANSFER_MANAGE). Roles: `WAREHOUSE_MANAGER` (new: all WMS permissions plus everything STORE_MANAGER has); STORE_MANAGER gets all WMS permissions; STORE_OPERATOR gets WMS_VIEW, PUTAWAY_MANAGE, PICKING_MANAGE and TRANSFER_MANAGE. No demo warehouse-manager user was created: there is still no demo-user mechanism.
- Document numbers follow the implemented format: transfer orders `TO/YY/NNNNN`, waves `WV/YY/NNNNN`, cycle counts `CC/YY/NNNNN`.
- Scanning: confirmation accepts the scanned bin and batch codes next to the quantity; a code that does not match the task is refused (SCAN_MISMATCH) before anything moves. A destination bin may also be identified by scanned code alone. There is no barcode or RFID hardware integration (REQUIREMENTS defers it).

## R15 PLM (2026-10-04)

- Lifecycle (PLM-005) lives in a new column `products.lifecycle_status` (DEVELOPMENT, PROTOTYPE, APPROVED, ACTIVE, PHASE_OUT, OBSOLETE), separate from `products.status` (DRAFT/ACTIVE/OBSOLETE master-data state). Existing and newly created products default to ACTIVE, so nothing about how they are ordered or produced changes.
- No ordering or production blocking for PHASE_OUT/OBSOLETE products. REQUIREMENTS PLM-001..005 specify none (PLM-005 only says transitions are audited), and CLAUDE.md says to enforce only what is specified. If wanted, it is a new rule with its own task, tests and a decision here.
- Lifecycle moves one step forward at a time, with a mandatory reason, and OBSOLETE is terminal (the spec lists a ladder and no way back). Each move writes a `product_lifecycle_events` row and a `PRODUCT_LIFECYCLE_CHANGE` audit entry (old value, new value, reason) in the same transaction. The service refuses skips, backward moves and a blank reason without leaving a trace.

It does not submit or activate the draft: the old BOM is superseded only when the engineer takes the new revision through DRAFT, ENGINEERING_REVIEW, APPROVED and ACTIVE (DESIGN section 21.2 step 2 is narrowed accordingly). The change description is stored in the revision's `change_reason`; the engineer edits the lines of the DRAFT with the normal BOM update because the ECO has no structured line-change format to apply.
- Implementation is all or nothing and runs under a row lock on the ECO. It fails with BOM_NOT_ACTIVE when an affected product has no ACTIVE BOM, and with ILLEGAL_STATE_TRANSITION when the product already has an open revision (DRAFT, ENGINEERING_REVIEW or APPROVED), which would otherwise collide on the revision letter. ## AR invoicing of dispatches and frontend permission guards (2026-10-04)

- Root cause of the missing AR invoices: `ArService.computeDispatchValue` was a stub that always returned zero, so the invoice and its journal had value 0, both journal lines carried debit 0 and credit 0 and violated `chk_jl_one_side_only`. That happened for every dispatch, not only zero-priced ones (the earlier hypothesis of a zero-priced line was too narrow). `DispatchService` caught and logged the exception, so no AR invoice and no revenue journal had ever been created for any dispatch.
- Invoice value is now the sum over the dispatch lines of quantity x unit price, each line rounded to 4 dp half-up. No tax is added (dispatch lines carry no tax data); GST arrives with the tax engine (R9-7.2).
- A dispatch worth zero (free samples, every line unpriced) gets a zero-value invoice with status PAID and no journal, because there is nothing to account for. Zero-priced lines among priced lines are simply left out of the journal.
- `JournalService` now normalises lines: machine-built journals drop zero-amount lines, a hand-entered journal with a blank or two-sided line is rejected with VALIDATION_FAILED, and any journal needs at least two non-zero lines. These used to surface as a database constraint error (HTTP 500).
- Invoicing runs after the dispatch commits: `DispatchService` publishes `DispatchCreatedEvent`, and `DispatchInvoicingListener` (AFTER_COMMIT) calls `ArReconciliationService.attempt`, which uses `ArService.autoCreateFromDispatch` in its own transaction. The invoice and its journal commit together (`postSourceJournal`), so one can never exist without the other, and a failure can never roll back stock that has left the warehouse (DESIGN 15.5).
- A failure is no longer silent. It raises a `MISSING_AR_INVOICE` alert (HIGH, one open alert per dispatch, repeats update it) through `AccountingFailureReporter` (own transaction), and the alert closes itself when the invoice is created. `AccountingBridgeService` does the same for inventory journals it cannot post (no account assignment, closed period, ...) with a `MISSING_JOURNAL` alert; a zero-value movement still posts nothing and raises nothing.
- Finding and fixing the gap: `GET /api/ar/reconciliation/missing-invoices` lists dispatches without an invoice (`AR_RECONCILE` or `AR_MANAGE`), `POST /api/ar/reconciliation/missing-invoices/retry` invoices them (`AR_RECONCILE`, audited as AR_RECONCILE_RETRY). It is idempotent: an existing invoice is left alone and V32 adds a unique index so a dispatch can never be invoiced twice. This is also the backfill for dispatches made before the fix: run the retry once after deploying. A dispatch dated in a closed or missing fiscal period keeps failing (and keeps its alert) until the period is open. No scheduled sweep was added.
- V32 seeds `AR_RECONCILE` for ADMIN and FINANCE_MANAGER, and gives FINANCE_MANAGER (ALERT_VIEW, ALERT_MANAGE) and ACCOUNTANT (ALERT_VIEW) access to alerts so finance can see these alerts. Review before go-live.
- Also fixed in the same code: AP and AR set the invoice status `PARTIAL`, which the V17 check constraint does not allow (`PARTIALLY_PAID`), so any partial payment or receipt failed. Covered by tests.
- The existing dispatch integration tests are `@Transactional` and roll back, so they never exercised the commit path. `ArFromDispatchIT` is deliberately not transactional.
- Frontend permission guards: the `admin/settings` route and nav entry required the literal `ADMIN`, which is a role code and not a permission, so the screen was unreachable for everyone. Both now use `SETTINGS_MANAGE`, as the backend does. A scan of every guard, nav entry, template directive and permission map found no other mismatch. `FrontendPermissionCodesIT` reads the frontend sources and fails if a code they check is not seeded or not granted to any role (it failed on the old code, listing `ADMIN`).

## R18 Advanced Manufacturing (2026-10-05)

- Migration is V33 (PLAN said V29; V29 to V32 were taken). It adds `machines.cost_centre_id`, `production_operations.scheduled_start/scheduled_end`, the spare part tables, labour/cost columns on `maintenance_requests`, the `mv_oee_daily` materialized view, GL accounts 5301 (Repairs and Maintenance Expense) and 5302 (Maintenance Labour Absorbed), the `MAINTENANCE_ISSUE` account assignment, the `MAINTENANCE_COST_UNPOSTED` alert type and the settings `mfg.calendar.shift_codes` (default `GENERAL`) and `mfg.schedule.default_horizon_days` (14). Migrations V1 to V32 were not touched.
- OEE follows DESIGN 24.1 with these precisions. Planned production time per day is the shift minutes of `mfg.calendar.shift_codes` on a working day (`hrm.weekly_off_days`, `hrm.timezone`). A non-working day that has recorded output counts as a planned day so overtime is not divided by zero. Days after today are left out and today counts only the shift time that has passed. Availability = (planned time - planned stops - unplanned stops) / planned time, i.e. planned maintenance counts against availability exactly as DESIGN defines it. Performance = ideal minutes of everything produced / operating minutes, capped at 100%. Quality = good / (good + rejected + scrap); DESIGN said good / (good + rejected), but `production_outputs` also has `scrap_qty` and scrapped pieces are not good, so they count. A range is the ratio of the summed minutes, never an average of daily percentages. Per day, downtime is clamped to the time available so a record that spills past a shift cannot make operating time negative.
- Reading OEE: for a fixed output, downtime only moves loss from availability to performance (OEE = good pieces x standard time / planned time). OEE falls when downtime costs output, and the Availability factor falls either way. The integration test models that (350 good pieces on the day with a one hour breakdown, 400 on the day without).
- Downtime categories are now a fixed set (BREAKDOWN, SETUP_CHANGEOVER, MATERIAL_SHORTAGE, NO_OPERATOR, MINOR_STOP, PLANNED_MAINTENANCE, OTHER). The CHECK is `NOT VALID`, so rows recorded before this release are untouched; new records are validated in `ProductionDowntimeService` (an unknown value is refused). Stored values outside the set, and a null category, count as OTHER (unplanned). Only PLANNED_MAINTENANCE is a planned stop. Preventive maintenance activities (`maintenance_requests.request_type = PREVENTIVE`) also count as planned stops; do not record the same time both ways. `POST /api/production/downtime` accepts an optional `endedAt` so a finished stop is recorded in one step.
- `mv_oee_daily` holds per machine and business day the good/bad pieces, ideal minutes and planned/unplanned downtime minutes. `OeeViewRefreshJob` refreshes it every 15 minutes (ShedLock). The trend chart reads the view (so it can be up to 15 minutes behind); the machine, summary, losses and reasons figures are computed live with the same query, and `OeeIT` proves the two agree. The business day comes from `ims.business_tz()`, which reads `hrm.timezone`, so a change of zone is picked up by the next refresh.
- Spare parts are materials. `SparePartService` creates a material of type `SPARE_PART` (same code) and keeps its name, UOM, minimum stock, reorder level and standard cost in step, so receiving, counting and issuing use the ordinary ledger, and the existing low-stock sweep (`AlertSweepJob` reads `materials.min_stock`) and MRP safety stock apply to them without new code. Stock is received through the normal purchase and goods receipt flow. Spare part stock is valued in 1401 Raw Material Stock (there is no separate GL account).
- Issuing a spare part (`POST /api/maintenance/requests/{id}/spare-parts`) allocates batches FEFO with the existing `BatchAllocator` and posts `MAINTENANCE_ISSUE` OUT legs through `InventoryPostingService` only. The line records the weighted average unit cost (`PostingResult` now carries `unitCost`). The auto-journal is Dr 5301 / Cr 1401, charged to the cost centre of the MACHINE: `AccountingBridgeService` asks each `JournalDimensionResolver` bean for a cost centre before falling back to the account assignment default, and `SparePartCostCentreResolver` answers for reference type `SPARE_PART_ISSUE`. Parts can be issued only while the request is OPEN or IN_PROGRESS; parts issued to a request that is later cancelled stay issued (there is no automatic return).
- Maintenance requests now have a state machine (rule 9): OPEN -> IN_PROGRESS -> COMPLETED, OPEN or IN_PROGRESS -> CANCELLED. `PUT .../status` used to accept any string. Request numbers now come from `DocumentNumberService` (`MR/26/00001`; they were `MR-<millis>`), a request for an unknown machine is refused, and the creating user is the authenticated user (the old code fell back to user 1). The `maintenance_activities` table had no API: `POST/GET /api/maintenance/requests/{id}/activities` now books and lists work (only while the request is OPEN or IN_PROGRESS).
- Maintenance cost (R18-5.1): labour = activity minutes x the labour rate of the machine's cost centre / 60 (the cost centre's `labour_rate_per_hour`; the machine's `cost_centre_id`, else the `controlling.production_cost_centre_id` setting). It is fixed on the request when it completes (`labour_hours`, `labour_cost`, `cost_centre_id`), so later rate changes do not move it. After the completion commits, `MaintenanceCostPoster` posts Dr 5301 / Cr 5302 to that cost centre through `JournalService` in its own transaction, once (idempotent; a request with no labour is just marked posted). A failure never undoes the completion: it raises a `MAINTENANCE_COST_UNPOSTED` alert (resolved on success), and `GET /api/maintenance/costs/unposted`, `POST /api/maintenance/requests/{id}/post-cost` and `POST /api/maintenance/costs/repost-unposted` find and retry it. 5302 is a contra-expense (labour is absorbed, not paid twice; payroll already books the salary). The `MAINT_COST` report lists labour and spare parts per machine for requests completed in a range. Existing machines were backfilled with cost centre CC-PROD-01.
- Scheduling (R18-3.x) is a pure forward finite-capacity engine (`scheduling.engine.ScheduleEngine`, unit-tested with hand-worked numbers). Order of work: order priority (1 = most urgent), due date (earliest first), order id, routing sequence. An operation lasts setup time + standard time x the planned quantity of its order (rounded up to whole minutes). It is placed on the machine that lets it finish earliest (ties go to the lower machine code), never before the previous operation in its routing ends, only in the working windows (`mfg.calendar.shift_codes` on working days) and never across another job: work may continue over non-working time, but if another job sits in between the attempt restarts after it, so the spans on a machine never interleave. A machine, once an operation has one (routing, an earlier run, or a manual move), is kept; the scheduler chooses a machine of the operation's type only for operations without one. An open maintenance request with a `scheduled_date` blocks that machine for the whole day (its duration is not recorded). Running operations and, in ONLY_UNSCHEDULED mode, existing windows block their machines.
- Operators come from the R13 data, read with SQL so HR stays unaware of planning (the HR architecture rule forbids other modules depending on `hrm`): an active employee with a login, skilled for the machine or the operation (skill matrix, not expired), not marked ABSENT/LEAVE/HOLIDAY on any day the operation touches, not on approved leave, and not already busy; the most proficient wins, then the one with least work, then the lowest user id. Not finding one is a warning (`NO_SKILLED_OPERATOR`, `NO_AVAILABLE_OPERATOR`), never a failure. Applying a run sets `assigned_operator_id` only when an operator was found.
- A run is a dry run (`POST /api/scheduling/run?dryRun=true`, nothing saved) or applied; mode FULL replans every pending operation in scope (dropping their windows first), ONLY_UNSCHEDULED plans only operations with no window. Moving one operation by hand (`PUT /api/scheduling/operations/{id}/schedule`): refused with 409 SCHEDULE_CONFLICT (a new error code) when the start is on another job or a maintenance day, or before the preceding operation in the routing ends; refused with 400 in the past and 422 when the operation is not PENDING; a start outside working time is moved to the next working time (`SNAPPED_TO_WORKING_TIME`); an overlapping next operation, a machine of another type and an unskilled or absent operator are warnings.
- The Gantt response carries the business time zone and each day's start and end instant, so the time zone of the browser never decides where a day starts. The chart is hand-drawn HTML/SVG (no chart library). Drag-to-reschedule uses pointer events; its geometry (pixel/time conversion, snapping, row choice) and the handlers that call the server are unit tested, but the drag itself was not exercised with a real mouse in a browser.
- New permissions: SPARE_PART_VIEW, SPARE_PART_MANAGE, SPARE_PART_ISSUE, MAINTENANCE_COST_VIEW, MAINTENANCE_COST_POST, OEE_VIEW, SCHEDULE_VIEW, SCHEDULE_MANAGE. Grants (REQUIREMENTS names no roles, so these are least-privilege choices that need business review): ADMIN all; MAINTENANCE spare part view/manage/issue, cost view, OEE; STORE_MANAGER spare part view/manage/issue; PURCHASE_MANAGER spare part view; PRODUCTION_MANAGER spare part view, OEE, schedule view/manage; SUPERVISOR OEE and schedule view; PLANNER schedule view/manage; MANAGEMENT spare part view, cost view, OEE, schedule view; CONTROLLER cost view; FINANCE_MANAGER cost view and cost post. `RoleAccessIT` now also creates PLANNER and CONTROLLER users.
- Not done / limits: there is no machine master screen, so the cost centre of a machine can be set through `POST /api/machines` (new optional `costCentreId`) but not in the UI; no demo user for the new permissions (there is no demo-user mechanism); machine calendars are the shared shift calendar (no per-machine shifts, holidays or capacity); a maintenance block takes the whole day; scheduling does not consider material availability; the OEE downtime form sends the local time of the browser for start and end.

Scope delivered (gate M19a): webhooks (R19-1.x), analytics views, BI query endpoint and dashboards (R19-2.1/2.2/5.1), a simplified builder (R19-2.3), demand-forecast seam (R19-3.1/3.2), anomaly sweep (R19-3.3), bulk import (R19-4.1), export (R19-6.1), read-only reporting schema (R19-6.2), Tally export (R19-6.4), degradation proof (R19-7.1).

- **Webhook secrets:** DESIGN 25.3 lists `secret_token_hash`, but an HMAC needs the secret, so it is stored AES-256-GCM encrypted (`IMS_INTEGRATION_SECRET_KEY`, 32 bytes base64), shown once, never read back; rotation replaces it. Signature header `X-IMS-Signature: t=<unix>,v1=<hmac>` over `t.body`; receivers reject old timestamps and de-duplicate on `X-IMS-Event-Key`.
- **SSRF:** https only, no credentials, host must resolve to public addresses (checked on save and again before every delivery). DNS can change between the check and the connection; restrict egress at the network layer too. `ims.integration.webhook.allow-private-targets` (dev/test only) relaxes it.
- **Retry schedule:** failure 1..6 retry after 1 min, 5 min, 15 min, 1 h, 4 h, 24 h; the 7th failure (initial attempt + six retries) is FAILED, raises `WEBHOOK_DELIVERY_FAILED`. Manual retry restarts the schedule.
- **Outbox is AFTER_COMMIT, not strictly transactional:** an event is queued in its own transaction after the originating one commits, so a webhook problem can never undo or block stock, an invoice receipt or a production close (R19-7.1). An event can be lost if the process dies between the commit and the enqueue.
- **Events:** `StockPosted`, `OrderCompleted` (= production order closed), `InvoicePaid` (= AR invoice fully received; new `InvoicePaidEvent` published by `ArService`).
- **Analytics:** fixed catalogue of 8 queries; finance ones also need `ANALYTICS_FINANCE`. Views count POSTED and REVERSED journals (a reversal posts the mirror image, so they net to zero). Views refresh hourly or via `POST /api/analytics/refresh`. Drag-and-drop builder is replaced by a controls-based explorer (query, period, columns, chart, axes, CSV).
- **Forecast seam:** `DemandForecastProvider` (named so to avoid clashing with the MRP `DemandForecastService`); default is manual. With `IMS_AI_FORECAST_URL` set, validated proposals are stored in `demand_forecasts` (notes "AI forecast ..."); a planner's forecast is never overwritten.
- **Anomaly sweep:** z-score on weekly material consumption, supplier pass-rate drop, machine yield drop and unplanned downtime jump; thresholds are `analytics.anomaly.*` settings. Findings are not auto-resolved.
- **Import:** CSV and XLSX, create-only, per-row transactions, dry run by default, unknown columns reject the file. **Export:** only the curated `reporting.*` views, keyset-paged and streamed, formulas defused, audited; finance entities need `ANALYTICS_FINANCE` too.
- **Reporting schema:** `ims_reporting` is NOLOGIN; a DBA creates a login role that is a member of it. If the migrating user cannot create roles the role is skipped with a notice.
- **Tally:** XML follows Tally's import schema (debits `ISDEEMEDPOSITIVE=Yes` and negative) but has not been verified against a live Tally.
- **Defect found and fixed:** `SpringSpecification` set its id from the product in its constructor, so every `ProductService.create` failed with "Row was updated or deleted by another transaction"; product creation through the API never worked.
- **Role grants (least privilege, REQUIREMENTS names none):** `ANALYTICS_VIEW` to ADMIN, MANAGEMENT, CONTROLLER, FINANCE_MANAGER, PRODUCTION_MANAGER, PURCHASE_MANAGER; `ANALYTICS_FINANCE` to ADMIN, MANAGEMENT, CONTROLLER, FINANCE_MANAGER; `TALLY_EXPORT` to ADMIN, FINANCE_MANAGER; `ANALYTICS_MANAGE`, `WEBHOOK_VIEW/MANAGE`, `DATA_IMPORT`, `DATA_EXPORT` to ADMIN only.

## Frontend/backend contract audit (2026-10-06)

## Usability gaps closed: inspection submission, AR reconciliation, DTO gaps (2026-10-06)

- **Inspection result screens.** `/quality/inspections/:id` records results for INCOMING, IN_PROCESS and FINAL inspections. INCOMING and IN_PROCESS: enter per-parameter values, then Save results (`POST /results`), then Accept or Reject (a reason is mandatory to reject). FINAL: Save measurements (`POST /results`) so a failed mandatory parameter is stored, a Quality Manager approves the deviation (`QUALITY_APPROVE`), then the final decision (`POST /final-decision`) with approved, rejected and hold quantities. The tolerance highlight is a client-side preview of `QualityInspectionItem.computeResult`; the server result is authoritative. First article inspections stay on their own screens (accept and reject refuse the FAI type).
- **Rejection reasons.** The UI requires reason lines that add up to the rejected quantity before a final decision. The backend does not enforce this: it silently skips missing reason lines. A backend rule would be a behaviour change and was not made.
- **Inspections with no plan parameters** cannot use `POST /results` (`items` is `@NotEmpty`), so they can only be accepted or rejected as a whole. The screen says so.
- **The old list screen was a stub:** its "Record Results" button posted zero quantities with an empty item list (always a 400), and Reject used the browser `prompt()`. Both are gone; the list links to the detail screen and can start in-process and final inspections.
- **AR reconciliation screen** (`/finance/ar-reconciliation`, `AR_MANAGE`): lists dispatches without an invoice and matches open `MISSING_AR_INVOICE` alerts by `entityType=DISPATCH`. The backend only has retry-all (`POST .../retry`, `AR_RECONCILE`); there is no per-dispatch retry. The last failure per dispatch comes from the most recent retry result, so it is not persisted across page loads. The alerts call needs `ALERT_VIEW` and degrades to no alert column without it.
- **Goods-receipt list:** `GET /api/procurement/goods-receipts` (`PURCHASE_VIEW` or `INVENTORY_RECEIVE`) with `status`, `purchaseOrderId`, `po` (PO number fragment), `from` and `to` (receipt date) filters, null-safe via `SearchText` and `QueryBounds`. `GoodsReceiptDto.poNumber` is now filled on every read; it was always null.
- **My Work:** the backend returns `ProductionOperationDto`, whose `id` is the production operation and `operationId` is the master-data operation. The screen used `operationId` as the key for start, pause and record-output, so it acted on the wrong operation id. It now uses `id`. `ProductionOperationDto` gained `productionOrderId`, `productionOrderNumber` and `productId` (additive), and `ProductionOrderDto` gained `priority` (additive). The contract guard matched by field name only and could not see the semantic mix-up; the three allowlist entries are removed.
- **Commit-path tests.** `InspectionCommitPathIT` is deliberately not `@Transactional` (`FinalInspectionIT` is): incoming accept and reject release or reject the material batch, a split final decision commits the FG batch status, the stock moves (AVAILABLE, HOLD, SCRAP) and the rejection record, a decision cannot be taken twice, and a repeated final-inspection-required event leaves one open inspection. It found no defect; the SPC feed after commit is already covered by `AdvancedQualityIT`.

## UI walkthrough blockers (2026-10-06)

Found by driving the real UI against a fresh install (see the walkthrough findings); fixed here: B1, B2, B6, plus the Administrator permission requirement.

- **B1, no administrator on a fresh install.** Nothing created a user, although README, RUNBOOK and the UAT checklist documented `admin` / `Admin@123`. Two paths now exist and share nothing:
  - *Dev/demo profiles:* `DemoDataLoader` step 0 creates `admin` with the documented dev password (BCrypt 12, no forced password change) and the loader runs as that real user instead of a fabricated id 1. The class is `@Profile({"dev","demo"})`, so the password constant never exists in a production build.
  - *Any other profile:* `InitialAdminBootstrap` creates the first administrator only when the `users` table is empty and `IMS_BOOTSTRAP_ADMIN_USERNAME` / `IMS_BOOTSTRAP_ADMIN_PASSWORD` are set (optional `IMS_BOOTSTRAP_ADMIN_EMAIL`). The password must pass the normal password policy (`AuthService.validateComplexity`), is stored as BCrypt(12), and is never logged; the user is flagged must-change-password and the creation is audited. With the variables unset the application starts normally and logs one line naming them. There is no default password anywhere in this path.
  - The must-change flag is advisory today (the login response carries it; there is no change-password screen, walkthrough finding M8).
- **B2, demo loader failed at step 10; real cause was in production code.** `ProductionOrderService.release` created the routing operations with `input_qty = 0` and only later operations received input (by cascade from the previous operation's good output), so no output could ever be recorded on the first operation. ## Finished-goods costing and COGS (2026-10-07)

Walkthrough 2 found that finished goods were never costed: output posted at unit cost 0, so the bridge skipped the FG receipt journal (Dr 1410 / Cr 1501) and the dispatch journal (Dr 5001 / Cr 1410). Revenue of 1,910 was booked with no cost of sales and WIP was never relieved. `AccountingBridgeService` skipped any movement whose `total_cost` was 0, with no log, no alert and no journal.

- **Root cause.** `OperationExecutionService.checkAndCompleteOrder` posted `PRODUCTION_RECEIPT` with a null unit cost and left `fg_batches.unit_cost` empty. An out-leg is valued at the balance's carried average cost, so the dispatch (which only passed the *selling price* as its unit cost, ignored for an out-leg) inherited zero as well. Material receipt and issue were already costed.
- **FG unit cost (`FinishedGoodsCostService`).** (1) With a RELEASED cost estimate the output is received at the estimate's standard unit cost (`total_standard_cost / cost_lot_size`, 4 dp). That is the only basis on which the controlling variance journal (Dr 5204 / Cr 1501 of actual - standard) relieves WIP exactly once. (2) Without one, it is received at the actual material cost still in WIP after scrap: (issued value net of returns - scrap relieved) / good quantity, 4 dp HALF_UP, never negative. Production does not depend on controlling: it owns the `StandardCostLookup` port and `ReleasedStandardCostLookup` in controlling implements it (`ControllingArchTest` still holds). Scrap value is read through `StockLocationQueryService.scrapValueOfOutputs`, so ledger reads stay in the query service.
- **Dispatch.** `SALES_DISPATCH` is posted with the FG batch's carried unit cost (the out-leg uses the balance average, which now holds the FG cost); COGS = quantity x that cost. Partial dispatches and batches at different costs work because each FG batch is its own balance.
- **No silent skip.** A zero-value movement of real stock whose type has an account assignment now raises a `MISSING_JOURNAL` alert ("zero-value movement (unit cost 0), so the GL does not reflect this stock"). `MATERIAL_CONSUMPTION` is GL-neutral and is ignored explicitly, like `STOCK_TRANSFER` (WIP is debited at issue and credited at FG receipt).
- **Rounding.** `unit_cost` is NUMERIC(18,4), so a unit cost that does not divide exactly leaves at most 0.00005 x quantity in WIP (for example 393.975 over 100 pieces: 3.9398 each, 393.98 received, 0.005 over-relieved). The journal always equals the ledger row, so Dr = Cr holds; the residual is a rounding difference in WIP, not a defect. `FinishedGoodsCostServiceTest` pins it.
- **Existing data.** No repair is provided. The ledger is append-only (rule 1), and the only zero-cost FG rows are from demo and test databases that were never production data; reload the demo data. A zero-cost FG batch in a real database would need a reversal and re-post, which should be a deliberate accounting decision.
- **Hand-worked scenarios (`FinishedGoodsCostingIT`, non-transactional, real services from PO to AR).**
  - Two receipts (40 kg x 50 and 40 kg x 60), 80 kg issued FIFO = 4,400, 100 good pieces: FG 44.0000 each; dispatch 60 gives COGS 2,640 and revenue 6,000; GL 1410 = 1,760 = ledger 40 x 44; WIP 0; the trial balance nets to 0.
  - Scrap: 4,000 of material, 6 scrap x 40 standard = 240 relieved, 80 good: (4,000 - 240) / 80 = 47.0000; WIP 4,000 - 240 - 3,760 = 0.
  - Released estimate (0.8 kg x 50 = 40.0000 per piece, conversion rates zeroed): FG at standard 4,000; actual 4,400 gives variance 400, Dr 5204 / Cr 1501; WIP 4,400 - 4,000 - 400 = 0, so nothing is relieved twice.

### Found, not fixed (accounting decisions needed)
1. **Production orders cannot be closed with the default settings.** `close` refuses while any issued material is unreconciled, and nothing reconciles it: there is no material-return endpoint, consumption exists only as `production.auto_backflush` (default `false`), and backflush itself is broken twice over. It only triggers when the first operation's sequence number is exactly 1 (routing steps are numbered 10, 20, 30), and it posts `MATERIAL_CONSUMPTION` with a null location, which the posting service rejects ("The given id must not be null"). So enabling the setting would break output recording. Fixing it properly needs per-order WIP tracking (a WIP balance is shared by every order that issued the same batch) and a return flow. The variance journal does not need a CLOSED order (COMPLETED is enough and controlling can re-run it), which is how the IT runs it. Recommendation: build material return and a consume-at-completion step together, decide whether leftover issued material is returned to stock or written off, then default backflush on.
2. **Conversion cost is never debited to WIP.** The variance journal credits WIP by (actual - standard), and actual includes labour, machine and overhead at cost-centre rates, but no journal ever debits WIP for them, so an order with a released estimate and non-zero rates leaves WIP negative by the applied conversion. Recommendation: a conversion-absorption journal at order completion (Dr 1501 / Cr an absorbed-conversion account), which needs an account and a policy for whose rates apply.
3. **Scrap can be charged twice under standard costing.** `PRODUCTION_REJECTION` posts Dr 5202 / Cr 1501 at the product's standard cost (DESIGN 15.3), and the variance (actual material minus standard for the good quantity) also contains the scrapped material as a quantity variance. DESIGN 15.3 and 16.3 both say so; the fix is a decision about which of the two carries scrap.

## Production order close, material reconciliation and scrap (2026-10-07)

Resolves items 1 and 3 of "Found, not fixed (accounting decisions needed)" above. Item 2 (conversion cost) is still open; see the end of this section.

- **What closing means (DESIGN 4.7).** An order closes from COMPLETED when every issued kilo is consumed, returned or written off. `OrderMaterialService` owns that: each `material_issue_lines` row carries `consumed_qty`, `returned_qty` and `written_off_qty` (V38), so every movement comes out of the batches the order itself issued. The WIP balance of a batch is shared by every order that issued it, so a per-order quantity could not be taken from the ledger.
- **Consumption.** The BOM quantity per piece (planned quantity without the scrap allowance) times the pieces the first operation has processed (good, rejected and scrap pieces all used material), never more than is still issued. `consumeForOutput` brings the order up to that target, so it runs after the first operation's output when `production.auto_backflush` is on and again when the order completes, and never consumes twice. The completion step makes the close work with the default setting; backflush only moves consumption earlier. The old backflush looked for sequence number exactly 1 (routing steps are 10, 20, 30) and posted with a null location, so enabling the setting broke output recording; it now uses the first operation by sequence order and the WIP location the material was issued to.
- **FG cost follows consumption.** Finished goods are costed from the material consumed (consumed quantity per line at the price it was issued at), not from what was issued, so leftover material never reaches FG. Whatever is left is returned or written off at close and relieves WIP on its own journal. With the existing scenarios (80 kg issued for 100 pieces) the figures do not change.
- **Return.** `POST /api/production-orders/{id}/material-returns` (`PRODUCTION_CLOSE`, an order that is RELEASED, IN_PROGRESS or COMPLETED) moves the quantity out of WIP (a `MATERIAL_CONSUMPTION` out-leg, GL-neutral) and into the raw-material location it was issued from (`MATERIAL_RETURN` in-leg at the issue price). The bridge journals it Dr 1401 / Cr 1501 (assignment seeded in V38). The batch gets its remaining quantity back, and its CONSUMED status if it had reached zero.
- **Write-off.** `POST /api/production-orders/{id}/close` takes an optional `{writeOffReason}`. Without a reason, unreconciled material refuses the close and lists it. With a reason, the remainder goes to the warehouse's SCRAP location as a `PRODUCTION_REJECTION` in-leg at its issue price (Dr 5202 Scrap Loss / Cr 1501), audited as `PROD_ORDER_MATERIAL_WRITE_OFF` with the reason.
- **Scrap is charged once.** Scrap recorded on the operations is relieved from WIP at the product standard cost when it is recorded (Dr 5202 / Cr 1501). Under standard costing the variance (actual minus standard for the good quantity) also contains the material of the scrapped pieces. The variance journal now posts `total variance - scrap already relieved`; the full total stays on the variance record for analysis and the scrap part is stored in `production_order_variances.scrap_relieved`. Hand-worked: actual 4,000, standard 94 x 40 = 3,760, scrap 6 x 40 = 240, so total 240 and journal 0; with the wire at 55 a kg actual is 4,400, total 640 and the journal 400. Before, the same scenario posted 240 twice and left WIP at -240. Without a released estimate FG is costed at actual material net of scrap, which was already charged once.
- **Variance and write-offs.** The variance's actual material cost excludes returned and written-off material (the latter has its own journal). A variance calculated before the leftover is returned or written off would include it, so the automatic variance on close runs after the reconciliation, in the same order the close does.
- **WIP in-leg.** The `MATERIAL_RECEIPT` in-leg that puts issued stock into the WIP location is GL-neutral like `STOCK_TRANSFER`; before, every material issue raised a false MISSING_JOURNAL alert.
- **Resolved on 2026-10-07 (option A, see "Conversion cost absorption" below): conversion cost is never debited to WIP.** The variance journal's actual cost includes labour, machine and overhead at the cost centre rates, but nothing debits WIP for them, so a released estimate with non-zero rates leaves WIP negative by the applied conversion. DESIGN 16.3 defines the variance but no absorption journal. Options: (A, recommended) post a conversion-absorption journal when the order completes, Dr 1501 WIP / Cr a new "Conversion Cost Absorbed" account at the cost centre's actual rates, with the real labour and overhead expense booked by payroll and the other cost journals, so the absorbed account clears against them at period end; (B) leave WIP at material cost only and have the variance journal exclude conversion, so FG is received at material standard and conversion is expensed directly; (C) receive FG at standard including conversion and take the whole conversion difference through the variance journal. A is the usual manufacturing-accounting treatment and keeps FG at full standard; it needs one new account and a rule for whose rates apply. Until one is chosen, orders with non-zero rates leave WIP negative by the applied conversion. The tests run with the rates zeroed.

## Conversion cost absorption (2026-10-07)

The user chose option A for the open item above: absorb the conversion cost into WIP when an order completes.

- **The journal.** When the last operation completes, `Dr 1501 WIP / Cr 5303 Conversion Cost Absorbed` is posted for the order's actual conversion cost (labour + machine + overhead), once. 5303 is a new credit-balance EXPENSE account (V39), the same kind as 5302 Maintenance Labour Absorbed. It clears against the real labour and overhead expense at period end; its balance is the under- or over-absorbed conversion cost. That period-end clearing is not built (payroll is not posted by cost centre); it is a reconciliation step for finance.
- **Amounts.** `ConversionCostCalculator` is the one calculation, shared by completion and the variance: elapsed time of each started and completed operation x the labour rate of the production cost centre (`controlling.production_cost_centre_id`, as before), machine rate only for operations on a machine, overhead = overhead % x (labour + machine). Hours keep 6 decimals; money is rounded half up to 4 places; the total is the rounded sum of the unrounded parts.
- **Fixed once.** `production` owns the `ConversionCostLookup` port and `OrderConversionCostService` in controlling implements it (ArchUnit: production never depends on controlling). The figures are fixed in the completion transaction in `production_order_conversion_costs` (V39), so the FG cost sees them and a later rate change moves nothing. The variance journal reads the fixed figures: actual cost = actual material + the fixed conversion total.
- **FG cost.** With a RELEASED estimate FG is received at the standard (material + conversion). Without one it is received at (material consumed - scrap relieved + absorbed conversion) / good quantity. WIP then nets to zero: issued material + absorbed conversion - FG at standard - scrap relieved - variance journal. Scrap is still charged once (variance journal = total variance - scrap relieved).
- **Posting.** After commit, in its own transaction, through `JournalService`; idempotent (the row is locked and the status moves PENDING to POSTED). No rate means no absorption: the row is `NOT_REQUIRED`, there is no journal and no alert. A failure (closed fiscal period, missing account) never blocks completing the order or receiving stock: the row becomes `FAILED`, a `MISSING_JOURNAL` alert is raised on the production order, and every variance calculation (`POST` on the controlling variance endpoint, or the close) retries it and resolves the alert. Orders that completed before V39 are fixed and absorbed the first time their variance is calculated.
- **No cost or profit centre tags on the absorption lines.** Tagged, the 5303 credit would reach the cost-centre actuals report with no real expense to offset it (payroll is not posted by cost centre) and every cost centre would show a negative actual. The order's cost centre is kept on the conversion-cost row. Tag the lines when real expense is booked per cost centre.
- **Hand-worked scenarios (`ConversionAbsorptionIT`, non-transactional, real services, a pinned `Clock`).** Standard: 3 steps of 24 min + 6 min set-up = 1.5 h a piece, labour 20 an hour, overhead 10 %, so 30 + 3 = 33 conversion + 40 material = 73 a piece (7,300 for 100). (1) 50 h an operation = standard: absorbed 150 h x 20 = 3,000 + 300 = 3,300, FG 7,300, variance 0, WIP 4,000 + 3,300 - 7,300 = 0. (2) 60 h an operation: absorbed 3,960, variance 7,960 - 7,300 = 660 (efficiency 600, other 60), WIP 4,000 + 3,960 - 7,300 - 660 = 0. (3) 94 good + 6 scrap: FG 6,862, scrap 6 x 73 = 438, variance 438 of which 438 is scrap, journal 0, WIP 4,000 + 3,300 - 6,862 - 438 = 0. (4) no estimate: FG (4,000 + 3,300) / 100 = 73.0000. (5) no rates: nothing absorbed, FG 40.0000. (6) retries and a later rate change post and move nothing. (7) a closed period: the order and the FG receipt still happen, the row is FAILED with an alert, and reopening the period and recalculating posts it and resolves the alert.
- **A `Clock` bean** (`ClockConfig`) now supplies the start and completion time of operations, so tests can make an operation take an exact number of hours; `TestClock` follows the system clock until a test pins it.
- **Limits.** Machine and labour rates still come from one cost centre (the production cost centre setting), not the operation's own work centre; efficiency variance is still labour only.

## AP three-way match (2026-10-07)

Business rule 18 and FIN-003 require a supplier invoice to reconcile to its goods receipt before it is paid. The second browser walkthrough showed a 25,000 invoice created, opened and posted against a 20,000 receipt, because `ApService` never looked at the receipt. The match is now enforced when the invoice is entered (V40).

- **What is matched.** The receipt value is what the goods receipt credited to GR/IR: received quantity x purchase-order rate per line, rounded to four decimals (`ThreeWayMatchCalculator`). Matching is at header level because `ap_invoices` carries totals, not lines. The receipt row is locked for the transaction (`ThreeWayMatchService`), so two invoices cannot both claim its open value. Procurement tables are read with SQL, so finance does not depend on procurement classes.
- **The rule.** An invoice may bill any part of the value still open on its receipt (a partial invoice), but not more than the open value plus the tolerance. Over that it is an EXCEPTION. The open value is the receipt value minus what other invoices already clear (cancelled and exception invoices do not count). A fully invoiced receipt has nothing open, so any further invoice is an exception that says so.
- **Tolerance.** `ap.match.price_tolerance_pct` and `ap.match.absolute_tolerance`, both seeded at 0 (exact), because neither REQUIREMENTS nor DESIGN gives a figure; the larger of the two applies. There is no quantity tolerance: the invoice has no quantity, so a quantity tolerance would have nothing to compare.
- **Under-billing is a partial invoice, not an exception.** Without invoice lines the match cannot tell a deliberate partial invoice from under-billing, and partial invoices must pass (12,000 + 8,000 against 20,000). A receipt that is under-billed in the end therefore leaves a credit on GR/IR; reviewing GR/IR is a finance reconciliation step, not built here.
- **Tax.** An invoice's tax is checked against the PO tax rate on what the invoice clears (same tolerance). Tax is posted to the new input-tax account 1301, never to GR/IR (before, tax was debited to GR/IR and left a residual there).
- **Required fields.** An invoice must name its goods receipt (`goodsReceiptId` is now mandatory, rule 18: there is no non-PO invoice in this system yet) and the receipt must be POSTED and from the same supplier.
- **Exception handling.** An invoice outside tolerance is saved as DRAFT with `match_status = EXCEPTION` and an explanation; it cannot be opened (so it cannot be paid). Two ways out: cancel the draft (`PUT /api/ap/invoices/{id}/cancel`, which frees the receipt) and enter a corrected one, or a finance manager approves the variance.
- **Override.** `POST /api/ap/invoices/{id}/match-override` needs `AP_MATCH_OVERRIDE` (ADMIN and FINANCE_MANAGER only) and a reason. The person who entered the invoice can never approve it, administrators included (`SEGREGATION_OF_DUTIES`), checked against `created_by`. The approval, with old and new status, the variance and the reason, is audited in the same transaction. It recomputes what the invoice clears against the value open at that moment, then the invoice is opened as usual.
- **Accounting.** Opening Dr 2401 GR/IR for the receipt value the invoice clears, Dr 5207 Purchase Price Variance for the part above it, Dr 1301 Input Tax Credit for its tax; Cr 2402 for the total. GR/IR therefore clears exactly the received value, and the price variance is booked once, visibly. New accounts 1301 (new group 13) and 5207. Invoices entered before V40 are marked `NOT_REQUIRED` (not re-judged) but their subtotal counts against their receipt, and they still post as before.
- **Not built.** No screen to enter AP invoices (the AP list shows the match status, the reason and the override action); no GR/IR reconciliation report; no credit notes (R9-7).
- **Tests.** `ThreeWayMatchCalculatorTest` (hand-worked figures) and the non-transactional `ThreeWayMatchIT`, which runs PO, goods receipt, invoice, override and journals through the real services with real users. The two older AP tests that created invoices with no receipt now live there (a receipt is required).

## Session, user administration and change password (2026-10-07)

Walkthrough majors M1 (a reload or deep link signs the user out) and M8 (no change-password screen), and the missing user-administration screens that left a single-administrator install without a second approver.

- **Root cause of the session loss.** The access token lives in memory only (ARCHITECTURE 10.1) and nothing asked the server for a new one when the app started, so every full page load began signed out although the HttpOnly refresh cookie was still valid. An `APP_INITIALIZER` now loads the runtime config and then calls `/api/auth/refresh`; the response already carries the full user and permissions, so no `/me` call is needed. It never navigates and never fails: with no valid cookie the router sends the user to login with the page they asked for. The access token is still never written to browser storage.
- **Return URL.** Guards, the login page and the change-password page carry a `returnUrl` and follow it only when it is an in-app path (`safeReturnUrl`: no other origin, no `//host`, no backslash or control characters, not a sign-in page).
- **401 handling.** Every 401 that arrives while a refresh is running shares that one refresh (single flight in `AuthService.refresh`) and is retried once; the retry goes straight down the chain, so it cannot start another refresh, and a second 401 on it ends the session. A rejected refresh ends the session once for every waiting request. The sign-in endpoints, including logout, are never retried.
- **Logout** now tells the server. `POST /api/auth/logout` is public on purpose: it acts only on the HttpOnly refresh cookie, so a tab whose access token has expired can still sign out. The browser state is cleared whether or not the call succeeds.
- **Two auth defects found by testing this against real PostgreSQL** (`AuthSessionIT`, both failed before the fix): `login` and `refresh` wrote and then threw, inside a rolling-back transaction, so the failed-attempt counter (account lockout) and the revocation of a reused refresh token's family (ARCHITECTURE 10.1, reuse detection) were never persisted. Neither feature had ever worked. `noRollbackFor = BusinessRuleException` on both methods.
- **A wrong current password is a 400, not a 401** (`CURRENT_PASSWORD_INCORRECT`). A 401 makes the browser refresh and sign out, over a typo.
- **A password change or reset ends the user's other sessions.** Their refresh tokens are revoked and `permission_version` is bumped, so the access tokens they hold stop validating. The session that changed the password keeps its own refresh token and takes a new access token (the screen refreshes once after the change). Access tokens of other sessions stop immediately, not after their 15 minutes.
- **User administration.** Screens for users (search, status filter, paging, create, edit with the optimistic-lock version, assign roles, deactivate with confirmation, reactivate; never your own account) and roles (permissions grouped by module). Creating a user with roles now needs `ROLE_MANAGE` on top of `USER_CREATE` (closes the gap recorded under the permission audit), unknown role codes at creation are rejected instead of silently dropped, and the initial password must meet the password policy (administrator-created users skipped it). Users created by an administrator have `mustChangePassword = true` (already the case).
- **Forced first-login change** *(the server now enforces it too: see "Auth hardening" below)*. The guards hold such a user at `/change-password` (remembering where they were going) and offer sign-out instead of cancel. **This is enforced in the browser only**: the server does not refuse other calls while a temporary password is in use. ## Auth hardening: server-side forced password change, admin reset and unlock, last-administrator guard (2026-10-07)

Three items left open by the session / user-administration pass. Three commits.

### 1. The forced password change is enforced on the server

- **Rule.** While `must_change_password` is set, `JwtAuthenticationFilter` answers every `/api/**` request except `/api/auth/**` (change-password, me, logout, refresh and the public sign-in endpoints) and `/api/system/ping` with **403 `PASSWORD_CHANGE_REQUIRED`** (RFC 7807, stable `code`). Non-API paths (actuator, docs) are not user data and are untouched. The refusal happens before method security, so a flagged administrator is refused on an endpoint they would otherwise be allowed.
- **Where the flag lives and how stale it can be.** It is part of `CachedUser` (the 60 s permission cache) rather than a JWT claim: a claim would stay wrong until the token expires, whereas the cache is evicted by whatever changes the flag. Every path that changes it (change password, password reset by token, admin reset) evicts the entry with `UserPermissionCache.evictAfterCommit`: once immediately, and once more after the transaction commits, which closes the race where a concurrent request reloads the pre-commit row between the eviction and the commit. The same operations bump `permission_version`, so tokens issued before the change stop validating at once. **Bound on staleness:** on a single node, none; with several nodes each holding its own Caffeine cache, at most the 60 s TTL (the same bound the permission cache already had).
- **Browser.** The error interceptor treats this code as a redirect to `/change-password` (the session is kept, so there is no sign-out loop, and no "no permission" toast). The route guard still sends the user straight there so they normally never see the refusal.
- **Tests.** `ForcedPasswordChangeIT` (real login and calls): an admin-created user starts flagged; an ADMIN is refused on ordinary endpoints; the allow-list stays open; after the change the old access token is 401 and the refreshed session works at once with no wait for the TTL; an unflagged user is never blocked. Tests that create users through `UserAdminService` (which flags them) and then call ordinary endpoints now clear the flag in their setup, as a user who has done the first-login change.
- **Bootstrap and demo.** Unchanged and consistent: the first administrator created from `IMS_BOOTSTRAP_ADMIN_*` starts flagged (they change the password through the allow-list); the dev/demo `admin` is created unflagged, as documented.

### 2. Administrator password reset and unlock

- **A dedicated permission.** `USER_PASSWORD_RESET` (V41, granted to ADMIN only), not `USER_UPDATE`: resetting a password lets the caller sign in as that user, so with `USER_UPDATE` any user editor could take over an administrator account. `unlock` is lower risk and needs only `USER_UPDATE`.
- **`POST /api/admin/users/{id}/reset-password`** `{reason (mandatory), temporaryPassword (optional)}`. Without a password the server generates one (at least 16 characters, all four character classes, no ambiguous characters, never containing the username) and returns it **once** in the response; with one, it must satisfy the normal policy and history rules and is not echoed back. Either way the account gets `must_change_password`, a bumped `permission_version`, every refresh token revoked, the lockout cleared and an entry in the password history. The password is stored as BCrypt(12), never logged and never audited; the audit entry (`ADMIN_PASSWORD_RESET`) records the reason and the flag change only. Request and response records mask the password in `toString`.
- **Not your own account.** An administrator resetting their own password gets 422 `SELF_PASSWORD_RESET`; they use Change password, which asks for the current one.
- **`POST /api/admin/users/{id}/unlock`** clears the failed-attempt counter and the lock-until time and is audited (`UNLOCK`); on an account that is not locked it does nothing. `UserDto` gained `locked` and `lockedUntil`.
- **Screens.** The user list gets Reset password and Unlock actions and a "Locked until" caption. The reset dialog asks for the reason, lets the administrator choose the password instead (with the live policy checklist) and shows a generated one in a copyable field with a "shown once" warning; it cannot be dismissed by accident while that password is on screen. Unit-tested only.
- **Tests.** `AdminPasswordResetIT`: generated password returned once and meets the policy; the old password, refresh token and access token all stop working; the very next request is blocked with the forced-change code; the audit row exists and contains no password; supplied passwords are policy-checked and not echoed; a reason is required; no self reset; a `USER_UPDATE`-only role can unlock but not reset; unlock restores sign-in and is audited. `RoleAccessIT` probes both routes (404 declared for a missing id).

### 3. The last-administrator guard

- **Invariant.** At least one **active, unlocked** user always holds ADMIN. `AdminGuard` enforces it for every path that can break it: `assignRoles` (taking ADMIN away) and `deactivate`. `deactivate`'s old check only looked at accounts whose *single* role was ADMIN, so an administrator with a second role could be deactivated as the last one; that gap is closed. A target that is itself locked is judged the same way: it is the *others* that must be usable.
- **Concurrency.** Both paths take a transaction-scoped Postgres advisory lock first (`pg_advisory_xact_lock`) and re-count after it, so two administrators demoting each other at the same moment are serialised and the second is refused with `LAST_ADMIN`. `LastAdminGuardIT` runs that race with two threads and fails 3 runs out of 3 when the lock is removed.
- **Other paths.** `RoleAdminService` and `RoleController` have no mutating operation (no role deletion, no permission removal), so nothing else can break the invariant today; `AdminHoldsEveryPermissionIT` already guards the ADMIN role's permission set in the data. A future mutating role path must call `AdminGuard`.
- **Known limit.** Failed sign-ins can still lock the only administrator temporarily (`auth.lockout.*`); the new unlock endpoint is the way back, but only an administrator can use it. A deployment with a single administrator should keep a second one for that reason.

## Segregation of duties across the approval workflows

- **Why.** SoD existed only for purchase orders, approval requests and the AP match override. A user could prepare, submit, approve and post their own journal, approve their own sales order and approve their own payroll run, and with the Administrator holding every permission one person could do all of it. The RUNBOOK and ARCHITECTURE 10.3 already claimed otherwise ("journal preparer != approver (hard-coded `AccessScopeService` check)" did not exist), so the documents were corrected to match the now-true behaviour.
- **The matrix** is in ARCHITECTURE 10.2a (document x step x who must differ x source x where enforced). Derived from the documents: SEC-008 and business rule 19 (PO, stock adjustment, journal), the RUNBOOK second-approver step (sales order), and the ARCHITECTURE section 10 principle "requester != approver" (payroll run).
- **Mechanism.** One helper, `common.security.SegregationOfDuties` (`requireDifferentUser`, `requireDifferentFromAll`), used by every service that has an approving step, including the existing PO, approval-request, AP-override and document checks (their messages are unchanged). It refuses with `SEGREGATION_OF_DUTIES` (422) and a message that names the document and says that a different authorised user must perform the step. There is no bypass flag and no Administrator exemption. An unidentified actor is refused; this cannot occur over HTTP because the JWT filter is the only code that creates an authentication.
- **Sales orders** record the confirmer in the new column `sales_orders.submitted_by` (V47; existing rows keep NULL and are checked against `created_by` only). The approval is refused for the creator and for the submitter. The DTO exposes `createdBy` and `submittedBy` so the screen can disable Approve for them.
- **UI.** Approve is disabled, with a tooltip giving the reason, on the journal detail screen (preparer), the sales order list (creator or submitter) and the payroll run screen (initiator), like the PO list. The server remains the authority.
- **Dispatch has no approval step**, so no rule applies. **Not required by the documents and therefore not enforced:** journal posting by the preparer after another user approved, journal reversal (a mirror of an approved, posted journal), payroll payment by the approver, period close and re-open, AP payment, purchase requisition / BOM / ECO / production order approval, CAPA verifier. These are listed in ARCHITECTURE 10.2a so a later policy change is a conscious step.
- **Tests.** `SegregationOfDutiesIT` (non-transactional, the real grants of every seeded role that holds `JOURNAL_APPROVE` or `SALES_APPROVE`, read from the database): no role can approve its own journal or sales order, a different user can, the creator and the submitter of an order are both barred, a system posting is not blocked. `HrmIT` SOD-PAY-1 covers the payroll initiator. The e2e spec `security/segregation-of-duties.spec.ts` drives the disabled Approve and the API refusal for a journal and a sales order. Existing tests that approved their own sales order, journal or payroll run now act as a second user (`TestData.asSecondUser`/`asUser`): ArFromDispatchIT, FinishedGoodsCostingIT, SalesOrderAuditIT, SalesDispatchIT, ReservationAllocationIT, FgRejectionAndTraceIT, ProductionFlowIT, JournalReversalIT and HrmIT (three payroll approvals). No assertion was weakened; the demo loader creates and confirms the demo order as `sales1` and approves it as the administrator.
- **Verified.** One clean `mvn clean verify`: 1253 unit/ArchUnit/web-slice tests and 2007 integration tests in 64 classes, 0 skipped, 0 failed (SegregationOfDutiesIT 5, HrmIT 19, WmsIT 18, DemoDataLoaderIT 8, InventoryPostingIT 11). Frontend: lint, format, 608 unit tests and the production build clean (new specs for the disabled Approve on the sales order list, the journal detail and the payroll run screens). The whole Playwright suite on a fresh database: 311 passed, 0 failed, 0 skipped (the 308 existing tests plus SOD-JRN, SOD-SO and SOD-SO-2). A first full verify found `WmsIT.approvedSalesOrder` approving its own order (5 errors), which is the new rule working; it now approves as a second user. The new tests were not run against the old code, so "they fail without the check" is reasoned, not demonstrated.
- **Not yet re-validated.** The two-consecutive-run release validation (cf530a2) predates this change; repeat it on this HEAD before claiming a new PASS.

## R9-7 finance completion (gate M9b, partly done)

Done, each with integration tests on hand-worked numbers (migrations V48-V52):

- **GST tax engine (R9-7.5, V48).** Determination is data: `tax_slabs` map a slab (GST18, GST12, GST5, GST0) and a supply type to tax codes; the supply type is INTRA when the company and the partner share a GSTIN state, INTER otherwise, and UT when both are in a union territory without a legislature (CGST + UTGST). Each tax code carries an input and an output GL account (1311-1314, 2311-2314). AP invoices take a slab (or a typed tax amount, never both); AR invoices tax each dispatched product under the slab in `product_tax_slabs` (a product without a slab is invoiced without tax, as before). An unregistered partner is assumed to be in the company state and the result says so. **The rates, the split and the state list are sample seed data (flagged) that finance must verify against the current GST schedule.** 18% on 20,000 intra-state is CGST 1,800 + SGST 1,800; inter-state it is IGST 3,600.
- **Multi-currency (R9-7.6, V49).** Decision #14 is resolved as the **transaction-date rate**, which with rates kept per fiscal period means the rate of the period containing the date. INR stays the functional currency: every journal is in INR. Suppliers and customers carry a currency; a foreign invoice keeps its currency and the rate it was booked at. The three-way match compares the invoice converted to INR. A payment or receipt at another rate books the **realised** gain or loss (4901 / 5208) against the carrying amount at the invoice rate, and the settling payment clears whatever INR is still carried, so rounding leaves no residue. Exchange rates have a maintenance endpoint (`EXCHANGE_RATE_MANAGE`). **Not done: unrealised revaluation of open foreign balances at period end** (the closing-rate method the decision weighed), and purchase orders are still in INR.
- **AR credit notes (R9-7.4, V50).** A credit note takes part of an open invoice off the receivable (Dr Revenue and the reversed output tax, Cr AR) at the invoice's own rate, so it never creates an exchange difference. Raised by one user, approved (posted) by another (segregation of duties). Tax is reversed in proportion; the final credit takes the exact remainder. A credit cannot exceed the open balance: **giving back money already received is not supported.** An optional customer return receives the goods as `CUSTOMER_RETURN` into QUARANTINE at the batch cost (Dr FG stock 1410 / Cr COGS 5001), limited to what was dispatched on the invoice. Returned stock waits in QUARANTINE: there is no re-inspection flow for it yet. The generated `ar_invoices.balance_amount` now subtracts `credited_amount`; the reporting view was recreated. AP debit notes are not part of R9-7.4 and are not built.
- **Module activation (R9-7.10, V51).** Twelve optional modules start active; `MODULE_MANAGE` (ADMIN) switches one off and its API then answers 403 `MODULE_INACTIVE`; the core is never gated. The navigation hides the screens by route prefix. **The switch gates the API and screens only**: automatic postings by other modules continue (the accounting bridge keeps journalling stock movements), so the ledger of record never silently loses an entry. "Tables of inactive modules stay empty" is therefore not guaranteed. The oee/scheduling/spare-parts screens live under `/maintenance` in the navigation, so they are not hidden by the route-prefix rule.
- **Step-up authentication (R9-7.9, V52).** SEC-010 names two targets, the trial balance and payment runs; they are `GET /api/gl/trial-balance` and `POST /api/ap/invoices/{id}/payments`. With `security.stepup.enabled` on, they need a re-authentication within `security.stepup.minutes` (5). **It ships switched OFF**: the requirement says configurable, and the prompt is only now in the frontend. The method is pluggable (`StepUpMethod`; PASSWORD today). A wrong credential is audited, never the credential itself. Period close, journal reversal and user-admin resets are NOT step-up targets because the documents do not list them. There is no rate limit on repeated wrong credentials beyond the normal login protections.
- **Business rules 16-19 (R9-7.3).** `FinanceIT` labelled its tests with an older numbering; they now match REQUIREMENTS (16 balance, 17 closed period, 18 three-way match, 19 preparer is not the approver) and each has a named passing test. **Question for the owner on rule 17:** the documents say posting into a closed period needs a Finance Manager override (audited). Today a closed period simply refuses every posting, and the only way through is a Finance Manager (PERIOD_CLOSE: ADMIN and FINANCE_MANAGER) reopening the period, which is audited with old and new status. I treated that as the override. The alternative is a per-journal override (post one journal into a closed period with a mandatory reason) which leaves the period closed; it is a new capability and was not built. Related: DESIGN section 15.6 asks for a mandatory reason when a period is closed, and the close and reopen endpoints take none.

Not done in this pass (see PLAN): plant scoping (R9-7.1, R9-7.2), budget vs actual (R9-7.7), purchase price variance capture (R9-7.8, partly present through the match variance), GST-ready reports (R9-7.11), and GC-1 to GC-6. Screens exist only for module activation and the step-up prompt; there are no screens yet for tax slabs, exchange rates, credit notes, or a GST slab and currency field on the invoice dialogs, so those are API-only and covered by integration tests, not by the browser suite.
